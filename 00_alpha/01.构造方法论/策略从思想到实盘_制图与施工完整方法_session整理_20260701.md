# 策略从思想到实盘：制图与施工的完整过程

> 本文档整理自一次完整讨论。主题：一个波动率凸性策略，从"只有一个想法"到"可实盘落地"，中间的完整过程性框架到底是什么，以及为什么过去大半年推不动。
>
> 整理原则：完整保留讨论中达成的全部判断，不遗漏、不篡改、不漂移。按主题重新分类组织，非按对话时序。

---

## 0. 问题起点

从 2025 年 10 月开始构思策略，一直推不下去。反思后的自我诊断：对"构建一个策略系统"的过程性宏观框架没有概念，一开始就陷入非常具体的细节（如策略语义），对整个搭建过程（先搭骨架、接口，而后填充）缺乏认识。

核心追问：搭建一个量化策略，从理念想法到最后可实盘落地，类似"盖房子"的过程到底应该如何？其中特别区分两个维度——**画图纸**与**按图施工**。

进一步的自我观察（这一观察是后续全部结论的种子）：

- 逻辑顺序（策略思想 → 策略语义 → Taxonomy Bridge → Engineering Specification）是图纸的**依赖结构 / 阅读顺序**，不等于**制图顺序**。
- 制图本身是一项施工，有独立的从 0 到 1 过程。
- 一直按逻辑顺序制图，导致漂移严重，画不出来。
- 过去实际推进中，把"画"和"补规范"两个环节混在一起：先画 → 卡住 → 发现少了什么（这个环节该怎么画）→ 返工写规范 → 继续画 → 又卡住 → 如此循环。

---

## 1. 对"盖房子"直觉的关键修正

房子事先知道能立住，问题只是施工顺序。策略不成立——事先不知道 edge 是否存在。

因此排序原则不是"施工依赖"，而是：**证伪成本最低的测试优先**（cheapest kill-test first）。整个生命周期是一串成本递增的"杀死测试"，每一步都可能把策略毙掉，排序目标是让坏想法尽早、最便宜地死。

"先挖地基"的方向对，但决定顺序的是证伪成本，不是施工依赖。

（说明：这是讨论早期给出的通用生命周期视角。后续讨论收敛到更精确的"制图 vs 施工"结构，本条作为背景保留。）

---

## 2. 漂移的机制（因果，非巧合）

逻辑顺序对应 depth-first 逐层做完。但第 N 层要画到多细、冻结在什么精度，是由第 N+1 层向它提的接口要求决定的。

不把一条线索一路走到 eng spec，就无法知道语义层该停在哪。于是逐层做完必然反复回头——每一次"卡住 → 发现少了什么 → 返工"，都是下游在向上游追讨接口契约。

**漂移的单一根因**：把"该由切片逼出来的规矩"当成"能提前写好的规矩"在做。顺序反了，所以越努力越空转。

---

## 3. 核心方法：先纵切一根，再横向铺开（walking skeleton）

正确的制图施工顺序，核心是一条原则：**先打一根垂直切片，再横向铺开。**

- 取一个最有代表性的元素，在最薄精度下，一路从思想 → 语义 → bridge → eng spec 打穿。
- 这根切片打穿的过程，**反向定义**出规矩（模块怎么分、接口承载什么、命名怎么定、每模块内部怎么画）——全是从切片里抽出来的，不是空想出来的。
- 规矩与第一根切片**共同涌现**，没有"规矩先、切片后"。
- 之后才横向复制这根已验证的切片到其余元素，此时"一个模块怎么画"已冻结，不再返工。

**否定的方案**：先把"制图脚手架/工具包（模块分解 + 接口 + 命名 + 存放 + 每模块内部画法）"完整搭好再开画——这个顺序不成立。完整前置的规矩层，恰恰是"空转"的成因。脱离实体单独设计的脚手架，无法知道自己该有哪些模块、接口该承载什么，于是它自身变成新的漂移源。

---

## 4. L0 / L1 的定义

**L1**：图纸本身。策略的实体内容——某个具体元素从思想到 eng spec 的那一条纵向内容。convexity_supply_vega 是什么、语义如何、映射到哪个工程对象、算法/字段怎么定，这是 L1。可回测、可施工的对象是 L1。

**L0**：画 L1 的规则。模块如何分解、接口承载什么契约、命名规范、存放结构、每类模块内部的画法模板。L0 不含任何策略内容，只含"怎么画"的约束。项目里的 B-2 治理层、TPL 模板、命名规范、manifest，全是 L0。

**关键关系**：L0 是 L1 的类型系统 / 语法；L1 是符合该语法的实例。语法不能脱离它要约束的句子去凭空设计——这是空转的根因，L0 被当成可独立完成的终端产物在精修。

---

## 5. 第一根 L1 如何产生

不是"设计"出来的，是**沿一个已定死的元素，强行走完全栈**逼出来的。步骤：

1. **选元素。** 挑一个满足两条件的：(i) 是策略核心而非边缘，删了策略就不成立；(ii) 会穿过所有关心的层（有语义、有 Greeks 耦合、有工程落点）。convexity_supply_vega 基本就是它——它是治理输入、有 scenario 条件、要落到字段。

2. **禁止预设 L0。** 手上不带任何模板、命名规范、模块分解开画。只带一个问题：这个元素，思想上为什么存在？

3. **逐层下推，每层只回答一个问题，答完立即下推，不求全：**
   - 思想层：它解决原型里的什么风险？（一句话，不展开分类学）
   - 语义层：它的定义是什么？输入是什么、输出是什么、什么条件下取什么值？只写到"下游能引用"为止。
   - bridge 层：这个语义对象映射到哪个工程对象？字段名、类型、单位。
   - eng spec 层：算法怎么算它？输入数据是什么、公式/伪代码、输出格式。

4. **在下推过程中记录每一次"卡住"。** 每次发现"这里得先定个规范才能继续"——不要停下来去建那个规范。把它记成一条 L0 候选（"命名需要规则""这里有个接口""这类对象需要模板"），然后用**当场最省的临时决定**继续往下走。切片必须一路打到 eng spec 落地。

5. **切片打穿后回看那张 L0 候选清单。** 此时才第一次有资格设计 L0——因为每一条都是被真实内容逼出来的，不是空想。这根 L1 同时产出了：一个可回测对象 + 一份有依据的 L0 需求。

**第一根 L1 的 DoD**：从思想到 eng spec 全栈贯通，末端是一个能喂给回测的具体对象（有输入、有算法、有输出格式），中途所有 L0 决定都是临时且被记录的。

**一句话**：第一根 L1 不靠规划产生，靠"选定一个核心元素、裸奔式打穿全栈、把卡点记为 L0 候选"产生。规范是切片的副产物，不是前提。

## 6. 垂直切片是否丧失全局观：全局拓扑 vs 全局接口

担心"垂直切片是局部构建、丧失全局观"是真问题，但"全局骨架先搭好"的解法会送回空转。

**垂直切片不是局部，是全局的一个纵剖面。** 丧失全局观的是"随便挑个边缘小模块打穿"。选 convexity_supply_vega，正是因为它是穿透性元素：它逼你回答标的是什么、Greeks 怎么耦合、治理输入从哪来、落到哪个工程对象。走完这一根，全局的"有哪些层、层间接口长什么样"已经被这根切片示范出来了。它是楼的一整根承重柱，从地基到屋顶，不是一块砖。

**把"全局骨架"拆成两类，结论相反：**

- **全局拓扑**（有哪几个层、层之间的依赖方向、大致边界）：**必须先有，而且已经有了。** 思想 → 语义 → bridge → eng spec 四层加治理，就是拓扑。一张纸画完，半天的事。它回答"哪里起步"。
- **全局接口契约**（每个模块精确的输入输出、字段、命名规范、内部画法模板）：**无法先搭，先搭必空转。** 因为某层输出该是什么精度/什么字段，只有下游向它提要求时才知道。不走切片，就是在猜接口。B-2 就是在猜——它试图脱离任何实体，先把所有接口契约定死，于是它自己变成漂移源。

**接口的性质决定它不能前置**：接口是两个模块之间的契约，契约由下游的真实需求定义，不由上游凭空声明。想先定义所有接口，等于想在没有任何一方到场的情况下签合同。空的合同必然要在真实交易发生时重签——这就是"卡住 → 返工 → 写规范 → 再卡住"的循环。

**顺序**：

1. **画全局拓扑（半天）**：四层 + 治理，层的名字、依赖方向、每层一句话职责。回答"哪里起步"。到此为止，不定接口、不定命名、不建模板。
2. **打第一根垂直切片**：沿拓扑纵穿一个穿透性元素。切片过程中，接口契约、命名、模板作为副产物被真实需求逼出来。
3. **固化 L0**：把切片逼出的接口/命名/模板收敛成规范。此时 L0 是有依据的。
4. **横向铺开**：拓扑已验证、接口已固化，其余元素按已冻结的规范快速填充。

**缺的不是"更大的脚手架"，是分清哪部分脚手架能前置、哪部分必须被切片逼出来。全局拓扑前置，全局接口不可前置。一直卡住，就是想把第二类当第一类做。**

## 7. files 逐份判定（三档）

**判据**：一个文档有用 ⇔ 它要么是**冻结的上游事实**（不可再生，只能引用），要么是**已验证的实例**（能当归纳模板的样本）。凭空正推出来的契约/模板/治理，全部不算。

### 第一档：上游事实，有用，只引用不再生

不可再生的语义锚或原始想法，是切片的源头：

- **QQQAI基金介绍.md** —— 最有用的一份。这是原型思想本身（降本循环 + 期限错配 + 双翼 backstop），是所有 L1 切片的思想层源头。是地基料。
- **T0 三件套**（主题树 / 12篇文档集 / 操作方法论主文档）—— 冻结语义锚。切片的语义层要向它们索引（如 T3 §2.1–2.4、D17–D20）。有用，但它们是**方法论边界**，不是可施工内容。
- **Greeks 主文档 / Trading Concepts 主文档**（v0.1.2-freeze 交叉修正版）—— 上游 Greeks/TC 语义权威。V_net 禁令、convexity_supply_vega 的合法定义源头在这里。切片语义层的核验基准。有用。

### 第二档：结构参考，部分有用

- **Taxonomy_Bridge 构建手册 v0.1** —— 有用，但当**方法学参考**，不当契约用。它讲"下沉如何防越权"，这套判据（哪些可下沉、下沉到哪、何种权限）在走切片 bridge 层时用得上。留作方法参照，不作前置规范。
- **Greeks_与_TC Field_Algorithm_YAML Bridge v0.1** —— 有用但降级。它是**唯一一份真正示范过"语义 → 字段/算法 taxonomy"下沉长什么样的实例**。当横向铺开、要归纳 bridge 层模板时，它是唯一的样本。现在别引用它的结论，留作后期归纳素材。

### 第三档：空演绎契约，当前基本无效

- **B-2 v1.3（PGC Bridge）** —— 空转的产物。它脱离任何可施工实体，把 Part A/B/C 的"承接关系"整份定死。A.1 的写法（"A.1 向 Part B 声明所需的 convexity responsibility""A.1 是需求提出方不是计算方"）是在无下游校验下声明接口契约，正是"猜"。**不是错，是没有校验资格。** 处置：不销毁，冻结旁置。走完第一根切片后，用切片逼出的真实接口回头对照 B-2，会看到它哪些条款有依据、哪些是空的。它变成**待验证假设集**，不是权威。
- **系统工程总纲 v0.3.1** —— 同类，更宏观的空演绎。它定义"全生命周期控制 + 规范装配宪章"，是 L0 的 L0。当前无效原因同上：脱离实体的元治理。旁置。

**结论**：有用的是**两端**——原型（QQQAI）+ 上游语义锚（T0/Greeks/TC）。中间那批 bridge/总纲/治理（B-2、总纲）是空演绎，不销毁，冻结旁置为"待切片验证的假设集"。过去大半年的工作量堆在第三档，这就是"做了很多却推不动"的原因。

## 8. 模块内部规范 / 模板为何不能前置

分两类，结论均为"事先写无效"，但机制不同：

- **模块级内部规范**（convexity_supply_vega 这一个对象：输入什么、输出什么、字段、算法）：事先写**无效**。原因不是"意象"，是它无处校验。写"输入 scenario、输出 vega floor"，这句话对不对、够不够、精度合不合适，只有当 bridge 层真的去引用它、eng spec 真的去算它时才暴露。事先写 = 在无反馈下声明契约，必漂移。这类"规范"应当是切片打穿后的**沉淀物**，不是前置件。

- **模板级规范**（TPL：任意一个语义对象**这类**东西该长什么样——有哪些必填槽位、命名怎么套、存哪）：事先写也**无效，但机制不同**。不知道"一个语义对象"通用长什么样，直到手工画完至少一个、最好两三个具体的。模板是从 2–3 个实例里**归纳**出来的，不是演绎出来的。现有的 TPL-02~06 是空演绎，所以套不上。

**统一判据**：凡是"契约/模板"，都必须由已存在的实例反推，不能由想象正推。一直在正推，这是漂移的单一根因。

**正确顺序**：先徒手填充 1 根（不靠规范，靠原型直觉），填完回看，规范自己浮现。

## 9. 完整流程（直白版复述）

### 第一步：手上到底有什么

十份东西只分两堆，中间夹一堆废动作。

- 一头是**想法本身**（QQQAI）：降本循环、卖短期权收钱、拿这钱养长期双翼、暴跌时 put 撑住、暴涨时 call 不踏空。这是"这栋楼为什么要盖、盖成什么样"。是源头。
- 另一头是**上游语义词典**（T0 三件套 + Greeks 主文档 + Trading Concepts 主文档）：不是策略，是策略要用到的"通用词汇的权威定义"（什么叫 convexity、什么叫 exposure shape、为什么净 Vega 不能当决策依据）。相当于盖楼要遵守的建材国标和力学规范。不能改，只能引用。
- 中间那堆（B-2、系统工程总纲）：过去大半年真正花力气做的，而它恰恰是空的。

### 第二步：中间那堆为什么是空的

想干的事翻译成大白话：**在真正画任何一张图之前，先把"以后每张图该怎么画、图和图之间怎么对接口"的规矩全定死。**

B-2 就是这个。整份文件在规定"哪个模块向哪个模块提什么、谁负责算、谁不许算"。

问题：**接口是两个模块之间的合同。合同的条款，是由下游真正用的时候提出来的，不是上游拍脑袋写的。**

具体例：A.1 说"我向 Part B 声明我需要的 convexity 责任"。可这个"责任"该写成什么样、精确到什么程度、用什么字段表达——只有当 Part B 真的拿这句话去算 convexity_supply_vega、算不下去、回头说"你这句话缺了个 scenario 条件我没法算"时，才知道。

没走到 Part B 真的去算那一步，A.1 里写的那套接口全是猜的。猜的合同，等真交易发生一定要重签。这就是反复经历的：画 → 卡住 → 发现少了个规矩 → 回去补规矩 → 再画 → 又卡住。每一次卡住，都是下游在向上游追讨一个当初拍脑袋签空了的合同。

结论：不是 B-2 写得不好，是"在画任何实图之前先把所有接口定死"这件事，**物理上不可能做对**。空转是必然，不是失误。

### 第三步：图纸该怎么画

既然接口不能凭空先定，正确顺序反过来：**先画一根从头到尾的真图，让接口在画的过程中自己冒出来，再把冒出来的接口固化成规矩。** 分四段：

**3.1 先画全局拓扑（半天）**：拓扑就是"这栋楼分几层、哪层压哪层"。已有：想法 → 语义 → bridge → 工程实现（字段/算法），四层加旁边的治理。每层一句话职责，画在一张纸上。**只画层和层的依赖方向，绝不在这一步定任何接口、任何命名、任何模板。** 这一步只回答"从哪儿起步"，答完就停。（过去的错误：想在这一步就把整栋楼每个房间的接口图都出了。）

**3.2 打一根垂直切片（核心）**：挑一个核心且穿透性强的元素（convexity_supply_vega）。**手上不带任何模板、不带任何命名规范，裸着**，沿拓扑往下走，每层只回答一个问题，答完立刻往下钻，不求全：

- 想法层：暴跌时 put 双翼要能撑住，得先知道"我到底需要多少凸性供给才算够"。
- 语义层：定义是什么、输入啥、输出啥、什么情景取什么值。去 T3、D18 索引词汇，去 Greeks 主文档核对（如确认不能用净 Vega）。只写到"下游能引用"就停。
- bridge 层：落到哪个工程对象、字段叫什么、什么类型、什么单位。
- 工程层：怎么算、输入什么数据、公式/伪代码、输出什么格式。一直打到"能喂给回测"。

**关键动作**：走的过程中一定不停撞墙（"这里得先定个命名规矩""这两个模块之间得有个接口"）。**撞墙时不要停下来去建那个规矩。** 记成一行清单，当场用最省事的临时办法糊过去，继续往下钻。切片必须一口气打穿到工程层落地。

**3.3 回看清单，这时才有资格定规矩（L0）**：切片打穿后，手上多了两样——一个真能算的 convexity_supply_vega 对象（可喂回测），和一张"撞墙清单"。清单上每一条都是被真实内容逼出来的，把它们收敛成规范，就是有依据的 L0。这一步产出的东西，才是 B-2 本该长成的样子。拿它对照旧 B-2：有些条款切片确实撞到了（有依据），有些切片根本没撞到（纯空想）。旧 B-2 从"权威文件"降级成"一份待验证的假设集"。

**3.4 横向铺开**：第一根切片验证了拓扑对、接口真实、规矩有依据。剩下的元素照这根跑通的切片、用固化的规矩，一个一个快速填。因为"一个模块怎么画"已冻结，不再返工。到这里图纸画完。

### 第四步：按图施工（图纸 → 实盘）

图纸画完，工程层每个对象都是"有输入、有算法、有输出"的可执行件。接下来是"量化开发"：

回测（先把一根切片端到端跑通再谈优化）→ 加成本滑点、参数敏感性、样本外 → 风险和仓位框架（put backstop 在这层权重最高）→ 模拟盘 → 小额实盘 → 监控和衰减 kill 准则。

这一整段接的是 3.2 段切片末端吐出来的那个工程对象。图纸和施工在这里对接。

### 一句话串全程

手上真正有用的只有两头——原型（QQQAI）和上游词典（T0/Greeks/TC）；中间辛苦做的 B-2/总纲是空转产物，因为"画图前先定死所有接口"物理上做不到；正确做法是先画一张楼层剖面（半天），然后裸着打穿一根垂直切片（撞墙就记账、临时糊过、继续钻），切片打穿后规矩自己浮现，这才是有依据的 L0，然后照这根切片横向铺满，最后按图施工进回测到实盘。

**过去卡住的根本原因就一句：把"该由切片逼出来的规矩"当成"能提前写好的规矩"在做。顺序反了，所以越努力越空转。**

## 10. 按图施工阶段：回测与实盘的关系

回测与实盘不是两个东西，是**同一套策略逻辑在两种数据源上跑**。理想状态：一份策略代码，喂历史数据就是回测，喂实时数据就是实盘。两者的联系不是"互相调用"，是"共用同一个核"。

```
        ┌── 历史数据 → 同一份策略逻辑 → 回测结果（研究参数）
策略逻辑 ┤
        └── 实时数据 → 同一份策略逻辑 → 实盘下单
```

分工：

- **回测层**：拿历史数据，反复试不同参数（roll 频率、双翼张数比、theta 预算占比……），找出"实盘该用哪组参数"。产出物是**一组冻结的参数**，交给实盘。
- **实盘层**：拿回测定好的参数，接实时数据，真的下单。产出物是**实际成交和 PnL**，回流成新的历史数据，喂回回测继续校准。

**闭环**：回测定参数 → 实盘用参数产生新数据 → 新数据回灌回测再校准。

**关键纪律**：回测和实盘必须**同源同码**。如果回测用一套逻辑、实盘用另一套，回测结论对实盘无效——这是量化最经典的死法。本策略尤其危险，因为 backstop 结构的价值全在极端路径上，而极端路径样本少，回测稍微失真实盘就废。"同一个核"不是洁癖，是生死线。

## 11. 图纸 → 实盘中间隔着什么（软件、架构）

图纸（工程层的字段/算法/伪代码）不能直接下单，中间隔着三样：

1. **数据**：从哪拿行情和期权链、历史怎么存、实时怎么接、时间戳怎么对齐（路径响应型策略，时间语义错一点，凸性判断就错）。
2. **计算/执行引擎**：把算法跑起来的软件。回测框架 + 实盘接口。
3. **券商/交易通道**：真正把单发出去的地方（IBKR 之类）。

一条最朴素的落地链：

```
图纸算法 → Python 实现 → 回测框架跑历史 → 定参数
                        ↓
                    同一份实现 → 接实时数据 → 券商 API 下单
```

工具层面，起步够用：Python + 一个回测库 + 期权数据源 + 券商 API。**不需要总纲里那套"多平面、数据治理、生命周期控制"的重型架构——至少现在不需要。**

### 施工阶段的架构也遵循同一规律

"这是另一个画图 → 实盘的过程吗"——是，但**不是又要先画一套施工架构图**。总纲里那些"系统平面/数据架构/时间语义/工具职责"，本质是施工阶段的 L0（施工规矩）。它和画图纸阶段的 B-2 是**同一个病**：脱离任何能跑的实体，先把整套架构规矩定死。

正确做法完全对称：

- 画图纸阶段，用一根**语义切片**（convexity_supply_vega 打穿四层）逼出图纸的 L0。
- 按图施工阶段，用一根**执行切片**逼出施工的 L0：拿那个已经画好的 convexity_supply_vega 工程对象，找最少的历史数据，用最糙的 Python 把它端到端跑一次回测，出一个 PnL 数字。

这根执行切片一跑，"数据怎么接、时间戳怎么对齐、引擎要什么、券商接口长什么样"这些问题会**具体地、被真实需求地**冒出来。跑通之后，回头看总纲那套架构，才知道哪些条款有用、哪些是空想。

**总纲的命运和 B-2 一样：不销毁，冻结旁置，作为待执行切片验证的假设集。**

**统一成一句话**：整个"想法 → 实盘"是同一个模式套两层。画图纸是一层，按图施工是一层。每一层的规矩（L0）都不能提前写，都必须由该层的一根最薄切片逼出来。现在手上堆着两份空演绎——图纸层的 B-2、施工层的总纲——都是同一个错误在两个阶段各犯了一次。

**动作顺序**：语义切片没打通之前，施工层的一切（回测、实盘、架构、软件）都还没有可施工的对象，谈架构就是又一次空转。语义切片打通 → 才有工程对象 → 才能打执行切片 → 才逼出施工架构。一根接一根，不能跳。

## 12. QuantConnect 回测 / IBKR 实盘的参数迁移差异

用 QuantConnect 做研究、回测，实盘用 IBKR，必然导致参数研究结果与实盘使用的差异。

**先拆概念**：把"能不能用"和"参数能不能直接搬"分开。"各家 Greeks 不会有数量级差异，否则谁都不可用"——这句话保证的是**策略在两个平台都成立**，不保证**回测定出的参数在实盘照搬有效**。这是两件事。

数量级不差，但本策略偏偏对这点差异敏感，因为它的判据全落在**阈值触发**上（凸性供给够不够、theta 收支平不平、保护力度到没到线）。阈值型判据的特点：变量差 5%，在阈值附近就是"触发 / 不触发"的二值翻转。所以不是数量级问题，是**正好卡在阈值上做决策**。

**真正的解法不是"证明两边 Greeks 接近"，是让实盘不依赖 QuantConnect 的 Greeks**：

- **在自己这层重算 Greeks。** 策略核心落脚点（Greeks、期权费收支、保护力度、目标仓位实际持有%）——不用 QC 的模型值，也不用 IBKR 的，用**自己的一份定价/Greeks 计算**，两个平台都喂同一份底层行情、跑同一份自己的算法。这样 QC 和 IBKR 只当**数据源和执行通道**，Greeks 由自己统一算。回测和实盘的判据就同源了。这正是"同一个核"的落地：核里必须包含 Greeks 计算，不能外包给平台。
- **对比验证仍要做，但目的变了**：不是拿它来决定能不能用，是拿它来标定自己那份算法——用 IBKR 实时链的隐波/Greeks 校准自己的定价模型，让"自己算的"贴近"实盘真实成交环境"。对比是校准手段，不是准入判据。
- **参数迁移的正确姿势**：回测定出的参数别直接进实盘，中间垫一层 **paper / 小额实盘**，用真实成交数据核对"回测预期的触发点"和"实盘实际的触发点"偏多少，把这个偏差作为参数的安全边际（阈值别贴着临界设，留 buffer）。backstop 结构容错低，这层不能省。

**一句话**：别追求两平台 Greeks 相等，追求 **Greeks 由自己那一份代码算**，平台只供数据和通道；对比验证降级为校准工具；参数靠 paper 层核偏差、留边际后再上实盘。

## 13. display / 职责分工的展开时机

策略是完整体系，不仅涉及怎么下单，也包括对当前账户持仓、成本滚动、Greeks 值及分布、市场状态等**事实层面**的 display 问题。不同职责根据不同工具的特点特长来选择使用——这**不是空的，是有实际意义的**。这一点成立。

问题是：这种分工什么时候展开？

自我判断（成立）：画图阶段（文本阶段）不涉及、研究部分不涉及、实盘必须考虑。

**补充的另一半**：它虽属于实盘阶段，但**不是实盘阶段一开始就展开，而是等实盘的那根执行切片跑通、确认核能真实下单之后，才展开。**

理由与前文同构。display（当前持仓、成本滚动、Greeks 分布、市场状态）、按工具特长分工——有真实意义**不等于**现在能被正确设计。它和 B-2、总纲是同一个判据：**脱离一个能真实产出数据的核，去设计"数据该怎么展示、哪个工具展示哪块"，就又是空演绎。** 因为"该显示什么、显示成什么样、哪个工具合适"，是由核真实吐出来的数据结构反过来决定的，不是先验能定的。

**正确触发时机**：

```
语义切片打通 → 有工程对象
执行切片打通 → 核能接真实数据、能真实下单、能吐出真实持仓/Greeks/PnL
        ↓  ←←← 到这里，"核吐出的数据结构"才第一次确定
display / 职责分工在此展开 —— 照着核真实吐出的数据去设计展示和分工
```

它属于**实盘阶段第一根执行切片跑通之后**的事：第一根执行切片解决"能不能真实跑通一笔"，跑通后核吐出的持仓/成本/Greeks 数据结构固定下来，这时"这些数据怎么 display、IBKR 看持仓、QC 看研究、自建面板看 Greeks 分布"这种分工才有对象可分。

**修正一格**：不是"实盘阶段就展开"，是"实盘的核跑通、数据结构落定之后才展开"。在那之前列分工表，等于对着还不存在的数据设计仪表盘。

## 14. 统一规律与完整动作序列

### 统一规律

凡是"规矩 / 架构 / 展示 / 分工"这类**二阶东西**，都不能提前设计，都要等它所服务的**一阶实体（核、数据）**真实存在后，被实体的形状逼出来。手上所有卡住的文件（B-2、总纲、以及正想动手的 display 分工），全是二阶的东西被提前做了。

### 完整动作序列（死的，没有第二条路）

```
语义切片
  → 工程对象
    → 执行切片
      → 真实数据结构
        → (回测定参数 / display 分工) 并行展开
          → paper 核偏差
            → 小额实盘
```

每一环的二阶设计都挂在前一环的一阶产出上。

### 现在唯一该做的第一件事

**打通第一根语义切片**（convexity_supply_vega 打穿思想 → 语义 → bridge → 工程四层）。它没打通之前，施工层的一切（回测、实盘、架构、软件、display）都还没有可施工的对象，谈架构就是又一次空转。
