## ⚠ 端点来源分级（读结论前必读）

本任务后期（E18 起）大量使用 QC 的 REST API。**这些端点的来源不同，可靠性不同，
不可平等看待。** 记录方此前的各步记录未标注该差异，属记录缺陷，此处正式补齐。

**API 基址**：`https://www.quantconnect.com/api/v2/`
（见 `lean/constants.py:85` 的 `API_BASE_URL`）

**认证方式**：Basic auth，用户名为 user id，密码为 `sha256(api_token:timestamp)`，
另带 `Timestamp` 请求头（见 `lean/components/api/api_client.py:135-152`）

**该 API 是 QC 官方的**：QC 自行发布于 PyPI 的 `lean` CLI 完全建立在其上，
本任务 E2 的 `lean login`、E4 的 `lean cloud push`、E6/E11 的 `lean cloud backtest`
全部经由它。E20 中 research 环境 `config.json` 内的 `api-access-token`
亦为 QC 自行注入的同一 API 的凭据。

### +5 字节的精确成因：pull 在 Windows 上做 LF→CRLF 转换

```
本地 probe_E20_output.py : 229 字节
  CRLF (\r\n) 出现次数 : 5
  裸 LF 总数           : 5
  裸 CR 总数           : 5
  → 全部换行均为 CRLF，载荷共 5 行，故 +5 字节

归一化 CRLF→LF 后:
  字节数 : 224
  sha256 : 3cfaae8294e9b7504190d89ad9ed889919ea6a364dbea7d60b0c2b4609ccdbb1
  与目标值一致 : True
```

**同一现象作用于所有 pull 下来的文件**，以 `main.py` 复核：

| | 字节 | sha256 |
|---|---|---|
| 云端 | 880 | `b6944ac8…` |
| 本地 | 901 | `ada3d437…` |
| 差值 | **+21**（= 本地 CRLF 数 21） | — |

本地归一化 CRLF→LF 后 **== 云端内容，逐字节相同**。

**结论：`lean cloud pull` 在 Windows 上写盘时执行 LF→CRLF 转换。
内容零损失，差异纯为行尾表示。**

### 对 E5「指纹链」结论的补充

E5 曾判定「`main.py` 经 push→pull 往返后逐字节一致，可进入指纹链」。
该判定**在 E5 的比较口径下仍然成立**——E5 比较的是「pull 前本地」对「pull 后本地」，
两侧同为 CRLF，故一致。

但本步骤揭示了一个 E5 未覆盖的维度：**云端存储内容与本地落盘内容并不逐字节相同**，
差异为行尾转换。

**故指纹链的正确表述应为**：
- 本地↔本地（pull 前后）：可直接比对，哈希一致。
- **云端↔本地：必须先归一化行尾（CRLF→LF）方可比对**，否则哈希必然不等。
