# 00B｜结构原型说明：QQQAI 降本循环与期限错配原型

## 0. 文档定位与权限边界

本节用于说明本策略母结构的经验原型来源与术语边界。QQQAI 基金介绍可作为 `prototype / explanatory lineage / terminology calibration material`，用于解释“短端供血与成本摊薄循环、长端 long put + long call 双翼、期限错配全维度管理、动态 roll 维护 optionality 与凸性”这些母结构要件的来源与语义。

QQQAI 原型不得直接作为以下对象：

```text
H 层原则；
生产参数；
DTE / moneyness / strike / ratio / 张数硬规则；
收益承诺；
风险结论；
自动交易规则；
字段、算法、YAML 或 runtime binding 的直接来源。
```

其中涉及“持续降本”“成本归零”“暴跌不受伤”“暴涨不踏空”“put 张数约 2 倍”“call 张数约 1 倍”“长期期权开销小于短端收入”等表达，只能作为原型叙事、结构目标或参数候选，必须经本体系的账本、Greeks、期限错配、coverage、funding、scenario stress 与 Phase 4 governance 重新转译。

## 1. 原型一：期权降本循环

QQQAI 原型中的第一层机制是期权降本循环。其方法论转译不是“卖期权赚钱”，而是一个可审计账本循环：

```text
卖出短端虚值或近虚值期权
  ↓
收到 short-end OTM / extrinsic premium cashflow
  ↓
若轮空：权利金进入现金账本
  ↓
若接货：以 strike - premium 的折扣成本获得底层资产
  ↓
持仓偏多后，可通过 covered call 形成轮空收入或等效出货价
  ↓
轮空收入 + 出货价差收入 + 剩余库存折扣成本
  ↓
重新计算摊薄后成本
```

因此，短端供血的合法语义是：通过短端卖出期权取得的 extrinsic premium cashflow，为底层 Beta 持有成本、库存成本和长端双翼预算提供账本来源。成本摊薄循环的合法语义是：把轮空收入、接货折扣、出货价差、剩余库存成本和累计现金收入放在同一个可审计账本中，持续计算 post-action cost basis。

该机制不得被简化为：

```text
short premium = safe carry；
权利金收入 = 结构合法；
累计现金收入为正 = 策略无风险；
接货折扣 = 左尾保护；
covered call 出货 = 自动增强收益；
成本摊薄 = 无需治理的确定性过程。
```

## 2. 原型二：结构化期限错配

QQQAI 原型中的第二层机制是结构化期限错配。单独降本循环的缺陷在于：

```text
暴跌时，日常权利金收入累积形成的保护垫可能有限；
暴涨时，单纯卖短端期权可能只获得有限权利金，错过底层资产右尾收益；
短端供血若过度扩张，会积累 short gamma、assignment、库存与保证金压力。
```

因此，原型通过“卖短端期权进行降本循环 + 买入长期 put / call 双翼”把单纯降本循环升级为：

```text
短端虚值权利金收入
  ↓
覆盖长端 put / call 的 premium bleed / theta decay cost
  ↓
长期 put 提供左尾保护
  ↓
长期 call 提供右尾参与 / 不踏空
  ↓
期限错配使“降本 + 左尾保护 + 右尾参与”形成同一结构
```

在本方法论中，期限错配不是无条件套利，也不是普通 calendar trade。它是一种结构预算关系和风险承担关系：短端 premium income 需要覆盖长端 premium bleed，同时接受 IV term structure、skew、Vega、liquidity、execution cost、roll cost、库存、保证金与 scenario stress 检查。

## 3. 原型到本策略母结构的转译关系

| QQQAI 原型内容 | 本策略方法论转译 | 权限边界 |
|---|---|---|
| 短端卖 put / call 收取权利金 | 短端供血与成本摊薄循环 | premium ledger / cashflow ledger，不是 Greeks Theta |
| 轮空收入 | 累计现金收入 | 需进入账本，不自动证明结构合法 |
| 接货折扣 | 折扣后库存成本 | 需与库存、coverage、margin 联合审查 |
| covered call 轮空或出货 | 出货现金流 / 等效出货价 | 不是自动卖 call 规则 |
| 轮空收入 + 出货价差 + 剩余库存折扣成本 | post-action cost basis / 成本摊薄循环 | 不得替代 Phase 4 governance |
| 单独降本循环的左尾 / 右尾缺陷 | 需要长端双翼 | 不得把 pure wheel 写成同一母结构 |
| 长期 put | 左尾保护承担者 | 张数、moneyness、DTE 是参数候选，不是 H 层硬规则 |
| 长期 call | 右尾参与承担者 | 张数、moneyness、DTE 是参数候选，不是 H 层硬规则 |
| 卖短买长 | 期限错配全维度管理 | 需接受 IV / Vega / skew / liquidity / funding coverage 检查 |
| roll / 接货 / 出货 / 功能迁移 | 动态 roll 维护 optionality 与凸性 | roll 是功能迁移，不是机械展期 |

由此，本策略母结构四要件的 canonical 表达为：

```text
1. 短端供血与成本摊薄循环；
2. 长端 long put + long call 双翼；
3. 期限错配全维度管理；
4. 动态 roll 维护 optionality 与凸性。
```

## 4. 术语校准：premium income 不是 Greeks Theta

QQQAI 原型中的短端供血收入，按本体系统一转译为：

```text
short-end OTM premium income；
short-end extrinsic premium income；
短端虚值权利金收入；
短端卖出期权取得的 extrinsic premium cashflow。
```

它属于 premium ledger / cashflow ledger / funding ledger，不属于 Greeks Theta。

`Theta` 只作为期权价值对时间流逝的敏感度观察。short option 可以有 positive Theta exposure，但这不等于已经实现的 premium income、funding 安全或结构合法。长端买入期权的成本侧可以表述为 `long-end premium bleed / theta decay cost`，但必须与短端 premium income 分账。

禁止表达：

```text
短端 theta 收入；
theta 循环收入；
front theta income；
theta 收入覆盖 long option theta；
theta 收入大于支出即 funding 可持续。
```

允许表达：

```text
短端虚值权利金收入覆盖长端 premium bleed / theta decay cost；
short-end OTM premium income supports long-end premium bleed；
premium ledger 与 Greeks ledger 分账；
positive Theta exposure 不等于 realized premium income。
```


# 01｜A1 未来不可知、S(X) / Π(X) 与凸性构造

## 0. 文档定位

本文处理的问题是：在未来路径、波动率路径、宏观事件与尾部事件不可稳定预测的前提下，策略系统的设计支点应放在哪里。本文不讨论某一具体执行价、DTE、仓位比例、参数数值或下单规则，也不试图证明某个市场方向判断正确。本文在主题树中属于横切纪律，是后续证伪法、对象身份、参数治理、Greeks 管理与 workflow 权限分层的上位支点。

本篇主要权限层级：H。A1 定义策略设计的认识论支点，后续参数、proxy 与动作语义不得反向改写。

## 1. 核心结论

第一，系统不应以预测外部状态空间变量 `X` 为核心，而应构造异构系统状态响应 `S(X)`，并以标量 payoff functional `Π(X)` 表达可比较的收益形状。

第二，Jensen 凸性只作用于 `Π(X)`；`S(X)` 中的 Greeks、ledger、coverage、funding、可执行性与治理合法性必须分别守约，不能与 payoff 共用同一个标量目标。

第三，系统质量不由观点正确性决定，而由 `Π(X)` 在多路径、极端路径、路径置换与反例路径中的形状，以及 `S(X)` 各分量是否仍满足结构约束决定。

第四，在本策略语境中，凸性不是“买期权”的同义词，而是 `Π(X)` 在极端路径、路径剧烈运动、升波 / 降波转换与功能迁移中的有利形状。

第五，凸性有成本，因此凸性构造必须同时设计短端供血与成本摊薄循环、期限错配全维度管理、动态 roll 与治理边界。

第六，`H_identity_target` 是长期占有 target Beta 的目标持仓身份；`P_A` 是 target Beta 长期持有具有正期望的可证伪假设。二者不得合并。

## 2. 问题定义

如果系统把设计支点放在预测 `X` 上，那么当路径、波动率、流动性、相关性或制度环境偏离预期时，系统会把判断错误转化为结构性损失。对长期持有、短端供血与成本摊薄循环、长端 long put + long call 双翼、期限错配全维度管理与动态 roll 共同构成的结构而言，预测一旦被写成合法性来源，就会污染对象身份。

本策略的 `H_identity_target` 当前指向长期占有优质科技 Beta；该身份只定义策略维护的对象。`P_A` 则承担“该 target Beta 长期持有具有正期望”的可证伪命题。若 `P_A` 被反例持续攻击，系统必须提交 identity / target review 类响应；不得因为仍持有 long put 而跳过审查。

因此，方法论起点不是预测，而是构造。`S(X)` 回答系统在路径展开后处于什么状态；`Π(X)` 回答可比较的 payoff 形状如何变化。二者必须关联，但不得混成一个异构“收益函数”。

## 3. 方法论机制

A1 的推理链可以压缩为：

```text
未来不可稳定预测
  ↓
不以预测 X 作为结构合法性来源
  ↓
构造系统状态响应 S(X)
  ↓
提取标量 payoff functional Π(X)
  ↓
要求 Π(X) 在极端路径、扰动路径、置换路径中保持有利凸性形状
  ↓
要求 S(X) 中的 Greeks / ledger / coverage / funding / executability / governance legality 分别守约
  ↓
凸性成本通过短端供血与成本摊薄循环、期限错配全维度管理与动态维护处理
```

这里的 `X` 不是单一价格变量，而是市场路径、波动率路径、账本状态、流动性状态、组合状态与事件冲击共同构成的状态空间。

`Π(X)` 是标量 payoff functional。在适用条件下，Jensen 直觉只写为：

```text
E[Π(X)] ≥ Π(E[X])
```

`S(X)` 是异构系统状态响应，包含 Greeks、现金流与账本、coverage、funding、可执行性、尾部保护、右尾参与、治理合法性等分量。`S(X)` 不具备统一的标量凸性序；任何把 coverage 或 legality 作为连续惩罚项并与 PnL 一并最大化的做法，都必须先证明没有把硬约束降格为优化权重，否则构成类型误用。

波动率凸性结构要解决的张力是：保留长期 Beta，降低线性脆弱性，维持尾部响应，同时让长期凸性成本具备短端虚值权利金现金流来源，并通过成本摊薄循环嵌入长期 Beta 持有账本。

因此，`Π(X)` 的凸性目标必须与四类机制共同出现：短端供血与成本摊薄循环用于处理长期凸性成本、底层 Beta 持有成本与长端双翼预算；长端 long put + long call 双翼用于左尾保护与右尾参与；期限错配全维度管理用于融资可持续性、premium bleed 覆盖关系与 vega 期限结构管理；动态 roll 用于维护 optionality、Gamma 中心与功能承担关系。

## 4. 对本策略系统的落点

对结构设计而言，A1 要求策略先定义 `Π(X)` 希望具备的 payoff 形状，再用 `S(X)` 检查承担这些形状的工具、账本与治理状态。short put、long put、long call、roll、partial monetization 等工具不能替代上位目标。

对 Phase 分层而言，Phase 2 只计算事实与 raw exposure；Phase 3 可以基于事实生成诊断与候选；Phase 4 才能根据约束栈判断候选是否同时维护 `Π(X)` 的结构承诺和 `S(X)` 的合法状态。

对参数系统而言，参数 `θ` 只能调节已注册的实现自由度与 `Π(X)` 的实现形状，不能把某个历史路径上的收益最优写成 `S(X)` 的结构合法性。参数优化不应单纯最大化样本收益，而应检查路径依赖度、约束满足度、成本可持续性与反例路径中的守约能力。

对 Greeks 而言，Greeks 是描述 `S(X)` 局部风险响应和 `Π(X)` 局部形状的语言，不是结构本体，也不能单独定义结构是否成立。

## 5. 常见误用

第一，把“不预测”误解为“不观察”。本体系拒绝的是把路径观点写成结构合法性来源。

第二，把“凸性”误解为无条件买期权。若没有短端供血与成本摊薄循环、期限错配全维度管理与动态维护，凸性成本会成为长期侵蚀。

第三，把 `S(X)` 与 `Π(X)` 重新合并为一个优化目标。coverage、funding、可执行性与治理合法性不是可与 PnL 无条件加权的同质分量。

第四，把长期科技 Beta 的目标持仓身份与 `P_A` 正期望假设合并。身份定义对象是谁，假设接受证伪；long put 只缓释左尾损失，不证明 `P_A`。

## 6. 失效条件与反例

A1 的失效不是某次亏损，而是系统重新把预测写成支点，或把异构约束降格为数值优化权重。例如：候选动作的合法性依赖“未来大概率继续上涨”；参数集只因历史收益最高而上线；优化器通过降低 coverage penalty 换取更高 PnL；为降低成本删除 long put 或 long call；`P_A` 被持续证伪后仍因保险腿存在而拒绝 identity / target review。这些都构成对 A1 的破坏。

A1 的边界在于：如果目标不是长期占有 Beta、不是 option-centric 路径响应结构、也不要求尾部与右尾同时处理，则 `H_identity_target` 与母结构落点需要重新定义。

## 7. 可复用表达

```text
当系统面对不可稳定预测的状态空间变量 X 时，设计支点不应是预测 X，而应是构造系统状态响应 S(X)，并以标量 payoff functional Π(X) 表达可比较的收益形状。
```

```text
Jensen 凸性只作用于 Π(X)；S(X) 中的 Greeks、账本、coverage、funding、可执行性与治理合法性必须分别守约。
```

```text
H_identity_target 定义策略长期占有什么对象；P_A 定义该对象长期持有是否具有正期望。long put 只缓释左尾损失，不证明 P_A。
```

# 02｜A2 证伪法与反例工程

## 0. 文档定位

本文处理的问题是：策略系统如何被验证，什么叫失败，如何主动寻找反例。本文不把回测收益、Sharpe、胜率或某一组参数的历史表现作为结构正确性的证明，也不展开具体回测引擎、数据表或 YAML 配置。本文在主题树中属于横切纪律，是从 A1 的构造论进入系统验证论的关键环节。

本篇主要权限层级：H/P。证伪法作为验证纪律属于 H；具体反例模板、压力路径和测试口径属于 P。

## 1. 核心结论

第一，系统验证的目标不是证明策略有效，而是寻找能破坏结构约束、对象身份、阶段权限、参数稳定性、proxy 边界、语义权威与部署绑定的反例。

第二，亏损不必然等于失败；在结构约束内的亏损可能只是成本、路径损益或正常波动。

第三，最高级失败是对象身份漂移，即系统为了继续运行、解释历史表现或追逐局部收益，改变了原本承诺维护的对象。

第四，通过检验只表示“当前未被证伪”，不表示“已证明正确”“已找到最优”或“可绕过后续审计”。

第五，反例工程必须嵌入参数回测、路径置换、workflow 权限、候选动作审查和部署审计，而不能只作为研究阶段的思想口号。

## 2. 问题定义

传统策略开发容易形成一条证明式路径：发现信号，回测盈利，证明有效，上线执行。这种路径的危险在于，它把历史样本中的表现当成未来合法性的来源，并容易把样本最优参数、路径观点或 proxy 指标写成结构原则。

波动率凸性策略面对的是高不确定、强路径依赖、非线性损益、期权期限结构、流动性切换与账本约束共同作用的系统。这样的系统不应问“是否已经被证明有效”，而应问“哪些路径、扰动、执行条件、参数变更或语义滑移会让系统违反它自己的承诺”。

因此，验证的核心从证明转为排除：冻结结构约束集 `C`，构造路径和反例，观察哪些情形会使 `C` 被破坏。

## 3. 方法论机制

A2 的基本机制是：

```text
冻结结构约束 C
  ↓
定义对象身份、阶段权限与参数边界
  ↓
构造反例路径、扰动路径、压力路径、路径置换
  ↓
寻找 constraint violation / identity drift / governance bypass
  ↓
若未发现，则只能声明当前未被证伪
```

这里的反例不只来自价格路径。至少包括以下几类：

1. **路径反例**：先跌后反抽、急跌后降波、慢跌不升波、暴涨导致右尾缺失、低波长时间磨损、低 IV 震荡磨损路径、跳空穿透保护区。

   低 IV 震荡磨损路径：定义与反例地位见 `本文件 00A §5`；本篇只将其作为 `P_B` 的反例引用，不重复定义。

2. **结构反例**：为降低成本删除长端保护；为赚 carry 过度扩大 short gamma；为锁定利润导致 long vega 不足；roll 后功能承担者消失。
3. **权限反例**：Phase 2 的事实字段被直接用于治理裁决；diagnostic 被写成 approved action；candidate parameter set 被直接上线。
4. **proxy 反例**：某个 Greeks 净值、IV 指标、VIX 标签或仪表盘信号替代 coverage、funding、object identity 或 governance decision。
5. **参数反例**：参数集只在某类历史路径收益高；优化目标等同 max PnL；主观调节扩大后未重进 freeze；参数册互斥被破坏。
6. **工程反例**：YAML 反向定义 md；profile 改写 core；deployment binding 把账户规模、标的特征或 broker 限制写成策略本体。

强路径依赖本身不是失败。期权结构天然路径敏感，路径不同导致 PnL、Greeks、账本状态和执行机会不同是正常现象。只有当结构合法性、参数合法性或动作合法性依赖某个特定路径顺序、样本族或流动性条件时，强路径依赖才成为证伪触发器；若进一步导致约束破坏或身份漂移，才构成反例。

P 层假设若作为反例攻击目标，必须先以假设内容、理论依据、反例路径与失效判据槽位注册；未注册假设不得由回测临时补写为结构原则。本策略 T0 假设与反例路径的唯一权威定义位于本文件 `00A §5`；下游操作文档只能引用并补充操作承接，不得反向定义。

## 4. 对本策略系统的落点

对参数测试而言，回测、压力测试、路径置换与反例回放不应只输出最优参数集，而应输出路径依赖报告、压力测试结果、反例路径、约束违反记录与候选参数集。候选参数集进入 Phase 4 治理前，不得被视为 production parameter set。

对 workflow 而言，Phase 2 的职责是提供可审计事实与 raw exposure，不负责判断系统是否失败；Phase 3 可以生成 diagnostic 与 candidate；Phase 4 负责判断候选是否违反结构约束、对象身份和治理边界。

对文档工程而言，证伪法要求每个方法论节点都说明误用方式和失效条件。只写“原则是什么”是不够的，必须写“什么情况下这个原则被滥用或失效”。

对执行而言，任何动作都要经受至少三类检查：动作是否维护原功能，动作是否破坏对象身份，动作是否绕过治理权限。

## 5. 常见误用

第一，把回测盈利当成结构证明。回测只能提供弱验证与反例扫描，不能证明未来有效。

第二，把亏损当成失败。在结构约束内的 premium bleed、mark-to-market drawdown 或尾部保险成本不一定是失败。

第三，把所有路径敏感性都视为缺陷。期权结构如果完全不路径敏感，也就失去了很多凸性响应；真正要检查的是路径敏感是否破坏结构合法性。

第四，把参数优化当成证伪本身。优化器若只寻找高收益参数，反而可能制造过拟合；证伪需要主动攻击结构约束。

第五，把证伪法写成抽象哲学，而不进入字段保留、回测输出、审计日志和 Phase 权限。

## 6. 失效条件与反例

A2 失效的典型信号是系统开始使用“表现好”替代“守约”。例如，某个参数集在样本上收益高，但其右尾参与被大幅牺牲；某个候选动作降低 drawdown，但删除 long put 功能；某个 Greeks 指标显示改善，但 coverage by shares 被破坏；某个部署 profile 因账户规模限制改写策略核心。这些都不是局部优化，而是证伪对象。

A2 的边界在于：并非所有策略都需要如此强的证伪工程。若策略只是短期方向性交易，验证协议可以不同。但对本策略而言，长期演化、对象身份、参数治理和动态迁移共同存在，证伪法不可省略。

## 7. 可复用表达

```text
本体系的验证目标不是证明策略有效，而是主动寻找能够破坏结构约束 C 的反例。
```

```text
亏损不是最高级失败；最高级失败是系统为了继续运行或解释历史表现，改变了原本承诺维护的对象。
```

```text
通过回测、压力测试或反例扫描，只能说明当前未被证伪，不代表已经证明正确、最优或可绕过后续治理。
```

# 03｜A3 H/P/W 权限标注

## 0. 文档定位

本文处理的问题是：在同一套策略系统中，哪些内容是结构硬核，哪些是可调整保护带，哪些只是弱观点或当前状态判断。本文不展开某个具体 H/P/W 清单的最终字段化，也不把现有字段、参数或算法直接归类为定稿。本文在主题树中属于横切纪律，作用是防止观点、proxy、参数、诊断和候选动作越权。

本篇主要权限层级：H。H/P/W 是全稿的权限标注规则，不是某个实现层标签。

## 1. 核心结论

第一，H/P/W 是方法论权限标注，不是文本装饰。

第二，H 层定义对象身份与不可被经验收益直接推翻的结构承诺；P 层承接可被证伪、修正、替换的辅助假设；W 层只承接当前状态、路径弱判断和人工裁量输入。

第三，任何 W 层观点若直接决定结构合法性，均构成权限上移；任何 P 层参数若改写 H 层对象身份，均构成身份漂移。

第四，H/P/W 必须贯穿文档、参数、workflow、诊断、候选、治理与审计，而不能只存在于方法论章节。

第五，本策略允许观察、分类、弱判断和人工输入，但它们必须经由候选与治理流程，不能直接成为动作批准。

## 2. 问题定义

复杂策略系统最常见的混乱不是“不知道内容”，而是内容的权限错位。一个价格观点、波动率标签、Greeks 指标、回测统计、主观判断或参数优化结果，在局部上可能有用；但如果它被提升为结构合法性来源，就会污染系统。

本策略同时存在哲学前提、母结构、component、state slice、diagnostic unit、proxy、parameter、candidate action、governance decision、deployment profile。若不标注权限，系统很容易把“当前看起来有用的东西”写成“系统必须遵守的东西”。H/P/W 的作用，就是给每类内容分配操作权限。

## 3. 方法论机制

H/P/W 三层可以定义如下：

| 层级 | 含义 | 操作权限 | 失效后果 |
|---|---|---|---|
| H | 硬核 / 结构身份 / 路径置换不变 | 可触发否决、身份裁决、治理流程 | 触发对象身份漂移 |
| P | 保护带 / 可调辅助假设 | 可被证伪、回测、替换、修正 | 判断错误但对象不必失效 |
| W | 弱观点 / 当前状态判断 | 只能 inform timing、诊断或候选输入 | 失效属于正常损益或弱判断错误 |

在本策略中，H 层包括：未来不可知、不以预测为结构支点、构造 `S(X)` 并以 `Π(X)` 表达 payoff 形状、`H_identity_target`、母结构四要件、coverage by shares 顶层口径、参数系统不改写本体、YAML 不反向定义 md、profile 不改写 core、candidate 不等于 approved 等。

P 层包括：参数化阈值、回测变量、risk-equivalent Greeks 规则、proxy 构造方式、诊断标签、roll 触发条件、路径分类方法等。这些内容可以被证伪和修正，但修正不能反向改变 H 层。

P 层假设进入回测、压力测试或反例工程前，必须完成假设内容、理论依据、反例路径与失效判据槽位登记；登记只授权证伪攻击与候选修订，不授权参数数值或执行规则。

W 层包括：当前市场状态判断、路径弱观点、人工裁量输入、临时执行偏好、对某个 regime 的弱判断。W 层可以参与候选生成，但不能绕过治理。

## 4. 对本策略系统的落点

对文档而言，每个方法论节点应明确自己冻结的是 H 层、P 层还是 W 层。A1、A2、A3 本身偏 H；A5 proxy 治理偏 P 层边界；B3 动作语义中，动作功能身份可以偏 H，但具体触发条件多为 P/W。

对参数系统而言，结构常量册承接 H 层约束，参数化回测变量册承接 P 层可证伪自由度，主观调节变量册承接受限 W 层输入。三者不能混同。

对 workflow 而言，Phase 2 输出事实，不带 H/P/W 裁决；Phase 3 可以基于 P/W 生成诊断和候选；Phase 4 负责检查候选是否违反 H 层或 P 层约束。

对执行而言，即使 W 层判断很强，例如“当前极可能进入急跌路径”，它也只能生成候选或提高人工审查优先级，不能直接批准交易动作。

## 5. 常见误用

第一，把 H 层写得过大。若所有经验判断都被写成 H，系统将无法学习、修正和迭代。

第二，把 H 层写得过小。若母结构、对象身份、阶段权限、语义权威都被当成可调项，系统会在优化中丧失同一性。

第三，把 P 层回测结果提升为 H 层原则。例如某个参数在样本中表现好，就被写成不可变规则。

第四，把 W 层人工判断绕过候选和治理。例如人工认为“现在应该减保护”，但没有经过 coverage、funding、vega、身份边界和 post-action 审查。

第五，把 H/P/W 标注当作文字标签，而不落实到参数归册、字段权限、算法阶段和审计清单。

## 6. 失效条件与反例

A3 失效的典型反例是权限上移和权限下沉。权限上移包括：proxy 指标替代结构裁决、路径观点替代合法性、参数优化替代母结构定义、profile 替代 core。权限下沉包括：把母结构四要件当成普通参数、把对象身份漂移当成普通版本更新、把治理裁决当成 dashboard 展示。

当系统出现“某个指标看起来合理，所以允许动作”或“某个参数收益更好，所以结构原则应修改”的表达时，应触发 H/P/W 审查。

## 7. 可复用表达

```text
H/P/W 标注不是内容分类，而是操作权限分类。
```

```text
H 层定义对象是谁；P 层定义对象如何被可证伪地调节；W 层只提供当前状态和弱路径判断。
```

```text
任何 W 层观点直接决定结构合法性，任何 P 层参数反向改写 H 层身份，均构成权限越界。
```

# 04｜A4 对象身份守恒与演化裁决

## 0. 文档定位

本文处理的问题是：在系统持续演化、参数调整、roll、功能迁移、profile 外置、工程部署和文档升级过程中，如何判断该系统仍是同一个策略对象。本文不讨论某个具体动作是否应当执行，也不冻结某组对象身份字段。本文在主题树中属于横切纪律，负责把 A1 的收益函数构造与 A2 的失败定义落到对象治理上。

本篇主要权限层级：H。对象身份守恒属于结构身份约束，任何实现演化都不得绕过身份裁决。

## 1. 核心结论

第一，本策略维护的对象不是某条 option leg、某个 Greeks 暴露、某个参数集或某个执行动作，而是一个持续演化的组合状态对象。

第二，对象身份由母结构四要件、当前主应用、收益函数形状、账本生存边界、阶段权限与治理规则共同维持。

第三，演化不等于身份漂移；roll、置换、参数调整、profile 绑定都可以发生，但必须保持结构功能与权限边界。

第四，身份漂移的最高风险来自下游对象反向定义上游对象，例如参数优化改写结构原则、YAML 改写 md、deployment profile 改写 core、proxy 改写治理。

第五，任何系统升级都应先判断是同一对象内部的实现演化，还是需要重新定义对象。

## 2. 问题定义

波动率凸性策略天然不是静态持仓。短端期权会到期，长端保护会衰减，long call 可能线性化，long put 可能进入或离开 gamma 区，账本成本会变化，vol regime 会切换，参数会更新，工程 profile 会外置，部署标的可能扩展。若把对象身份绑定在某条腿或某个瞬时 Greeks 值上，系统就无法演化。

但如果演化没有边界，系统又会在优化和执行中悄悄变成另一个东西。比如为了降低成本删除长端保护，为了提高收益扩大 short vega，为了适配账户限制改写母结构，为了方便 YAML 生成新增语义规则。A4 要解决的就是：允许演化，但不允许偷换对象。

## 3. 方法论机制

A4 只裁决“是否仍是同一对象”，不负责展开运行时状态字段。对象身份守恒需要同时检查四层：

1. **目标层**：当前主应用是否仍是长期占有优质科技 Beta，并通过衍生品结构改写线性脆弱性。若目标改变，原对象需要重定义。
2. **母结构层**：短端供血与成本摊薄循环、长端 long put + long call 双翼、期限错配全维度管理、动态 roll 维护 optionality 与凸性是否仍共同存在。删去任一项，都不是同一对象。若删除成本摊薄循环，只保留短端权利金收入，则第一母结构要件失效；若删除长端 put / call 任一侧，左尾保护或右尾参与失效；若把 QQQAI 原型中的 put 2x / call 1x 等示例写成 H 层硬参数，则构成参数越权。
3. **功能承担层**：具体承担者可以迁移，但功能不能消失。roll、置换、partial monetization、风险改形都必须说明它维护了什么功能、转移了什么功能、是否削弱了关键功能。
4. **治理权限层**：事实、诊断、候选、批准、执行、审计的权限链不能被打断。任何跳过治理的演化，均不能以“策略适应市场”为理由合法化。

对象身份不是静态字段，而是跨时间的守恒关系。一次操作前后，系统可以改变 lot、expiry、strike、moneyness、Greeks、现金流与账本状态，但必须保持结构功能与约束承诺。

## 4. 对本策略系统的落点

对 roll 而言，roll 不是展期，而是功能迁移。判断 roll 是否合法，不看它是否保持原合约，而看它是否维护 optionality、Gamma 中心、高阶凸性、账本关系与母结构功能。

对 partial monetization 而言，部分兑现不是“赚钱就卖掉”，而是反脆弱激活后期的账本重分配动作。它不能削弱长端保护到身份漂移，也不能绕过 post-action 合法性审查。

对参数系统而言，参数集只能调节结构身份内的自由度，不能通过优化改变母结构四要件、coverage 顶层口径、Greeks 聚合范围、risk-equivalence 规则、scenario-stress 边界、resolver 输出边界或候选与生产的区分。

对部署工程而言，profile 负责绑定 core、参数集、L0 配置、底层标的与账户；profile 不得把标的特征、账户规模、broker 限制写成策略核心。

## 5. 常见误用

第一，把持仓不变误认为身份不变。某些静态持仓虽然未变，但 long option 功能已衰减，结构响应已经退化。

第二，把持仓变化误认为身份改变。roll、置换、功能迁移本身不是漂移，只要功能守恒。

第三，把收益改善当成身份合法。若收益改善来自删除尾部保护或扩大负凸性，不属于同一对象内部优化。

第四，把工程部署差异当成策略扩展。不同标的、账户、broker、profile 只有通过 object identity review 后，才可被视为同一 core 的部署实例。

第五，把修正层工具提升为本体。VIX、LETF、overlay、双层 sleeve 等工具可以服务本体，但不能替代母结构。

## 6. 失效条件与反例

A4 失效的典型反例包括：删除 long call 后仍声称保留右尾参与；将纯卖 put wheel 写成同一策略；把短端虚值权利金收入误写成完整成本摊薄循环；把 VIX overlay 上升为母结构；参数优化把 `Π(X)` 退化为特定样本路径上的收益最大化，同时使 `S(X)` 的 coverage 或治理合法性失约；profile 为适配账户规模取消长端双翼；YAML 新增字段后反向要求 md 接受其语义。

当系统出现“为了方便执行”“为了提高收益”“为了适配账户”“为了降低成本”而改变母结构功能时，应触发身份裁决。

## 7. 可复用表达

```text
对象身份不是由某条腿、某个 Greek 或某组参数定义，而是由目标、母结构、功能承担关系与治理边界共同定义。
```

```text
合法演化允许承担者迁移，但不允许结构功能消失；允许参数变化，但不允许参数反向改写对象身份。
```

```text
当系统为了继续运行、解释历史表现或适配工程限制而改变原本承诺维护的对象时，构成身份漂移。
```

# 05｜B1 对象身份与状态本体

## 0. 文档定位

本文处理的问题是：系统实际维护的对象由哪些状态、模块和层级表达。A4 关注跨时间的身份守恒，B1 关注对象在运行时如何被表示。本文不展开字段表、数据库 schema 或具体计算算法。本文在主题树中属于运行脊柱，是后续 B2 权限链、B3 动作语义、C1 Greeks 风险语言的对象基础。

本篇主要权限层级：H/P。对象状态本体属于 H；具体状态表达模板与诊断挂载方式属于 P。

## 1. 核心结论

第一，系统维护的是组合状态对象，不是合约清单、信号模型或 Greeks 仪表盘。

第二，该对象至少需要表达市场状态、账本状态、结构状态和治理状态；缺一都会导致运行表达不完整。

第三，Module、component、state slice、diagnostic unit、proxy、parameter 是不同层级对象，不能互相替代。

第四，状态表达不等于动作裁决；对象状态模块负责表达当前对象是什么，不负责批准动作。

第五，Greeks、proxy、参数、profile 都应挂载在对象表达的适当层级上，而不能成为新的主模块或母结构要件。

## 2. 问题定义

如果没有清晰的状态本体，系统会出现三类混乱。第一，把事实当成判断，例如看到某个 raw exposure 就直接裁决结构非法。第二，把诊断当成本体，例如把 Greeks dashboard 写成第五模块。第三，把动作当成对象，例如用 roll 规则或 partial monetization 规则定义策略是谁。

波动率凸性策略需要长期运行，状态会不断变化。它必须知道当前账上有什么、市场处于什么环境、谁在承担左尾保护、谁在承担右尾参与、短端供血与成本摊薄循环是否仍可持续、期限错配是否仍守约、哪些候选可进入治理、哪些边界已触发人工审查。B1 的任务是给这些内容分层。

## 3. 方法论机制

B1 只处理“对象如何被表达”，不裁决演化是否合法；演化是否合法由 A4 处理，候选是否可执行由 B2 处理。运行对象可按四大模块表达：

1. **对象状态模块**：回答当前对象处于什么状态。包含市场状态、账本状态、结构状态 state slice、治理状态 state slice。
2. **母结构模块**：回答结构本体承担者是谁。包含短端供血与成本摊薄循环、长端 put、长端 call、期限错配全维度管理；其中动态 roll 是母结构四要件之一，其工程承接位置在迁移与执行模块，用于维护 optionality 与凸性。
3. **迁移与执行模块**：回答如何在不破坏对象身份的前提下迁移功能、生成候选、执行风险改形。
4. **治理与审计模块**：回答候选是否被批准，参数、版本、动作、profile、审计留痕是否守约。

状态本体可按以下表格表达：

| 状态类型 | 回答的问题 | 典型内容 | 禁止用途 |
|---|---|---|---|
| 市场状态 | 外部环境当前是什么 | price path、vol surface、skew、term structure、liquidity、event shock | 不直接生成动作授权 |
| 账本状态 | 账户与持仓当前是什么 | option lots、underlying shares、cash flow、premium ledger、coverage、funding | 不替代结构身份判断 |
| 结构状态 | 母结构功能当前由谁承担 | short-end premium funding & cost-dilution loop、long put、long call、tenor mismatch、roll optionality、component state slice | 不把某一 leg、某个现金流或某个 Greek 写成结构本体 |
| 治理状态 | 候选、约束与审计当前处于什么状态 | constraint stack、candidate status、approval/block、manual review、post-action check、audit trail | 不把 dashboard 或 diagnostic 写成裁决 |

在这些模块内部，还要区分 component、state slice 和 diagnostic unit。component 是职责宿主；state slice 保存当前状态结论；diagnostic unit 解释当前状态并可能生成候选输入。它们不是同一类对象。

例如，Greeks raw exposure 属于事实或暴露表达；Greeks by tenor / moneyness / expiry 属于观察和 proxy；Greeks diagnostic 属于诊断；Greeks-related legality 属于治理。若把 Greeks 直接写成母结构 component，就破坏了对象层级。

## 4. 对本策略系统的落点

对 Phase 2 而言，B1 要求事实层必须保留账本真相、option lot、现金流、底层库存、premium ledger、cost basis ledger、raw exposure、bridge view 和 recomposed view。它们是对象表达的底座。

对 Phase 3 而言，diagnostic unit 基于事实和 proxy 解释结构是否钝化、集中、失衡、进入某类路径响应状态，但它只生成诊断和候选，不批准动作。

对 Phase 4 而言，治理状态需要记录 constraint stack、approval / block、manual review、post-action check、parameter governance 和 audit trail。

对文档系统而言，B1 要求每个术语都标明自己是对象、状态、component、proxy、参数还是动作。未定义主语会导致后续写作和工程实现不断混层。

## 5. 常见误用

第一，把状态字段当成裁决。状态只说明当前是什么，不自动推出允许什么动作。

第二，把 component 写成模块。component 是职责域，不是新的 L1 module。

第三，把 state slice 写成诊断器。state slice 持有结论，diagnostic unit 负责计算和解释。

第四，把 proxy 写成对象。proxy 是观察工具，不是系统维护的对象。

第五，把参数系统写成第五模块。参数系统是横切治理能力，不承担母结构本体职责。

## 6. 失效条件与反例

B1 失效的反例包括：对象状态只显示 PnL 而不显示账本和功能承担；把短端权利金现金流显示为收入字段却没有接货、出货、剩余库存成本、累计现金收入与长端双翼预算之间的账本关系；市场状态被直接写成动作规则；结构状态缺失导致不知道谁在承担左尾或右尾；治理状态缺失导致候选动作无法审计；参数对象和业务字段混表导致参数变更污染事实层。

当系统无法回答“当前对象是谁、处于什么状态、哪些功能仍被承担、哪些候选已被批准”时，B1 没有成立。

## 7. 可复用表达

```text
系统维护的对象不是某条腿、某个 Greek 或某个动作规则，而是一个由市场、账本、结构与治理状态共同表达的组合状态对象。
```

```text
component 承担职责，state slice 保存状态结论，diagnostic unit 解释状态并生成候选输入；三者不得互相替代。
```

```text
对象状态表达不等于动作裁决；当前是什么，不自动推出应该做什么。
```

# 06｜B2 事实 → 诊断 → 候选 → 治理的权限链

## 0. 文档定位

本文处理的问题是：系统如何从事实计算走向动作裁决，哪些阶段只能观察，哪些阶段可以诊断，哪些阶段可以生成候选，哪些阶段才能批准或阻止执行。本文不写具体字段、算法步骤或 order instruction。本文在主题树中属于运行脊柱，是防止 Phase 权限混乱的核心方法论文档。

本篇主要权限层级：H。事实、诊断、候选、治理的权限链是全稿 canonical 表述。

## 1. 核心结论

第一，Phase 不是工程进度编号，而是方法论权限分层。

第二，Phase 2 只负责 facts、raw exposures、bridge views、recomposed views 与数据质量，不做诊断、不生成候选、不批准动作、不做最终治理裁决。

第三，Phase 3 负责 diagnostics、Greeks Observation、risk-equivalent / scenario-stressed inputs、candidate action、candidate parameter set、repair proposal，但不直接执行。

第四，Phase 4 负责 constraint stack、approval / block、manual review、post-action legality check、audit trail 与 object identity drift declaration。

第五，candidate 只表示可提交治理审查的候选对象，不表示已批准、可执行或可上线。

## 2. 问题定义

策略系统最容易发生的越权是从“事实看起来不对”直接跳到“动作必须执行”。例如 raw exposure 出现某个数值、Greeks dashboard 显示失衡、coverage 下降、VIX 上升、参数候选收益较好，系统就直接触发动作。这样的路径绕过了诊断、候选生成、治理审查和执行后合法性检查。

对于波动率凸性策略，事实、诊断、候选和治理必须分开。事实层越权会把数据字段变成裁决器；诊断层越权会把解释变成动作；候选层越权会把可能性变成批准；治理层缺失会使系统无法审计为什么执行。

## 3. 方法论机制

权限链可表达为：

```text
Phase 2：事实与 raw exposure
  ↓
Phase 3：诊断与候选生成
  ↓
Phase 4：治理裁决与执行审计
```

Phase 2 的输出包括当前账本、持仓、市场快照、raw Greeks exposure、premium cash flow、coverage summary、bridge view、data availability、calculation status。它回答“现在是什么”，不回答“意味着什么”或“应该做什么”。

Phase 3 的输出包括 diagnostic label、candidate action、candidate parameter set、repair proposal、manual review trigger。它回答“当前状态可能意味着什么”“可以提交哪些候选”，但不回答“是否批准”。

Phase 4 的输出包括 approval、block、manual review、constraint violation、post-action legality check、audit trail、identity drift declaration。它回答“候选是否可以变成动作”“执行后是否仍守约”。

这条链条要求每个对象都带权限状态。`raw exposure` 不是 `diagnostic`；`diagnostic` 不是 `candidate`；`candidate` 不是 `approved_action`；`approved_action` 也必须接受 post-action check。

B2 同时冻结三条输出不变式：

```text
不变式 1：candidate 只能由 Phase 3 生成；Phase 4 的 governance / audit 不得直接生成 candidate。
不变式 2：no_action_observation 是 Phase 2 事实记录；no_action_decision 是 Phase 4 治理裁决。二者同名语义不得混用。
不变式 3：audit 若发现需要修复，只能输出 repair_review_request 并返回 Phase 3；禁止 audit → candidate / approved action / order 的短路。
```

动作的目的是维护结构凸性。Phase 2 可以记录 `no_action_observation`，但其不含治理含义；只有 Phase 4 在完成约束检查后才能形成 `no_action_decision`。持续无动作期间，凸性状态与对象身份审计按治理参数周期触发；audit 如发现修复需求，只能输出 `repair_review_request` 返回 Phase 3，验证周期为 `parameter_slot_candidate`。

## 4. 对本策略系统的落点

对 Greeks 而言，Phase 2 可以计算 raw Greeks by lot / tenor / option type / side；Phase 3 可以进行 Greeks Observation、risk-equivalence、scenario stress 和候选触发；Phase 4 才能判断 Greeks-related legality。

对 partial monetization 而言，Phase 2 只提供所需事实输入；Phase 3 生成 PM candidate；Phase 4 检查 post-action 是否破坏 coverage、funding、vega、对象身份和治理边界。

对参数而言，参数测试环节只能产生 candidate parameter set；Phase 4 参数治理决定是否上线、回滚或阻止。candidate parameter set 不等于 production parameter set。

对 dashboard 而言，显示不等于裁决。监控面板可以显示 facts、diagnostics 和 governance status，但 dashboard 上出现红色信号不等于自动批准动作。

## 5. 常见误用

第一，把 Phase 2 当作治理层。事实计算越多，越需要限制权限，而不是让事实字段直接裁决。

第二，把 diagnostic 写成 action。诊断只能解释状态，不能替代候选与治理。

第三，把 candidate 写成 approved。候选对象只是进入审查队列，不具备执行权限。

第四，把 post-action check 前置为简单预估。执行后合法性必须检查真实成交后的状态，而不是只用计划值。

第五，把 Phase 当成工程排期。Phase 是权限层，不是先后完成文档的编号。

## 6. 失效条件与反例

B2 失效的反例包括：raw exposure、未声明等价规则的 Greek 净额或 dashboard signal 直接触发交易；diagnostic label 自动生成 order instruction；回测候选参数自动进入生产；manual review 被标记后仍自动执行；执行后没有重新计算对象身份和约束状态。

当系统无法区分 fact、diagnostic、candidate、approved、executed、audited 这些状态时，B2 没有成立。

## 7. 可复用表达

```text
Phase 是方法论权限分层，不是工程进度编号。
```

```text
Phase 2 只回答当前事实是什么；Phase 3 回答当前状态可能意味着什么以及可以提交什么候选；Phase 4 回答候选是否被批准以及执行后是否仍合法。
```

```text
candidate 不是 approved action，diagnostic 不是 candidate，raw exposure 不是 governance decision。
```

# 07｜A5 Proxy 治理

## 0. 文档定位

本文处理的问题是：指标、仪表盘、代理变量、压缩摘要、诊断标签在系统中如何使用，如何防止它们替代对象身份、结构约束和治理裁决。本文不定义具体 proxy 字段清单，也不冻结某个 dashboard 设计。本文在主题树中属于横切纪律，服务于 B2 权限链和 C1 Greeks 风险语言。

本篇主要权限层级：P。proxy 选择和压缩方式可替换，但 proxy 不得越权成为治理裁决这一限制属于 H。

## 1. 核心结论

第一，proxy 是观察和压缩工具，不是事实真相源、对象本体或治理裁决器。

第二，任何 proxy 必须声明其来源、聚合范围、适用场景、允许用途和不得用途。

第三，proxy 可以 inform diagnostic、candidate 或 manual review，但不能直接批准动作。

第四，Greeks、VIX、IV-RV、term structure、skew、coverage summary、risk label 都可能成为 proxy；它们的共同风险是“看起来像结论”。

第五，proxy 治理的核心不是减少指标，而是限制指标权限。

## 2. 问题定义

复杂系统需要 proxy，因为完整对象状态过于复杂，不可能每次都直接观察全部 lot、现金流、期限、moneyness、Greeks、流动性和治理状态。proxy 提供压缩视图，有助于观察、诊断和沟通。

但 proxy 的危险在于，它会被误认为真实对象。例如，未声明等价规则的 vega 汇总被误认为期限错配状态，未声明等价规则的 delta 汇总被误认为整体方向风险，VIX 被误认为压力充分性，coverage summary 被误认为保护合法性完整表达，dashboard 红灯被误认为动作批准。A5 要解决的不是是否使用 proxy，而是 proxy 的权限治理。

## 3. 方法论机制

一个合法 proxy 至少需要五项声明：

```text
source：来自哪些 facts / raw exposures / views
aggregation scope：跨哪些维度聚合，未聚合哪些维度
assumption：依赖什么情景假设或等价规则
allowed usage：允许用于观察、诊断、候选还是治理输入
forbidden usage：不得替代什么上位对象或裁决
```

proxy 权限应按链条向下限制：

```text
facts / raw exposure
  ↓
proxy / compressed view
  ↓
diagnostic input
  ↓
candidate trigger input
  ↓
governance input
```

除非经过明确授权，proxy 不得跨级跳到 governance decision。即使某个 proxy 被允许成为治理输入，也仍只是 constraint stack 的输入之一，不是单点裁决。

A5 到此只给出 proxy 元规则；Greeks 的 node-level 表达、non-netting 与风险等价规则由 C1 细化。任何跨 tenor、call/put、leg type、moneyness、side 的聚合，都必须声明等价规则。未声明者只能作为 rough observation。

## 4. 对本策略系统的落点

对 dashboard 而言，面板应明确区分 facts、proxy、diagnostic、candidate、governance status。尤其是 Greeks dashboard，应显示为 Risk Response Dashboard，而不是 Action Approval Dashboard。

对 Phase 3 而言，proxy 可以帮助诊断结构钝化、风险集中、期限错配、vega regime、gamma center、burn pressure 或 funding stress，但诊断输出仍只是 candidate input。

对 Phase 4 而言，proxy 只有在被明确纳入 constraint stack 后，才可成为治理输入；并且不得替代 coverage by shares、premium-based funding relation、对象身份或 post-action legality。

对文档工程而言，任何出现“指标显示 X，所以系统应做 Y”的表述，都要改写成“指标提示 X，可生成候选 Y，并进入治理审查”。

## 5. 常见误用

第一，把 proxy 当事实真相源。proxy 可能来自事实，但不是事实本身。

第二，把 proxy 当对象身份。例如用某个 vega 净值定义期限错配本体。

第三，把 proxy 当动作触发器。例如 VIX 达到某值就自动执行结构变化。

第四，把 proxy 当约束裁决。例如 未声明等价规则的 Greek 汇总改善就认为动作合法。

第五，把多个 proxy 加权成综合评分后，忘记其仍不是治理裁决。

## 6. 失效条件与反例

A5 失效的反例包括：dashboard 红灯自动下单；VIX 高位自动降低保护；未声明等价规则的 vega 汇总值替代 tenor-level vega map；IV-RV 扩大直接扩大 short premium；coverage summary 替代 lot-level coverage；综合风险分数替代 constraint stack。

当 proxy 的使用者无法回答“这个指标来自哪里、压缩了什么、不能用于什么”时，该 proxy 不具备治理资格。

## 7. 可复用表达

```text
proxy 是观察工具，不是对象本体；proxy 可以进入诊断和候选，但不得直接替代治理裁决。
```

```text
任何 aggregate metric 必须声明聚合范围、等价规则、情景假设和允许用途；否则只能作为粗观察。
```

```text
显示不等于裁决，仪表盘不等于治理引擎。
```

# 08｜A6 自由度治理：参数系统

## 0. 文档定位

本文处理的问题是：策略系统中哪些内容可以被参数化，参数如何注册、归册、回测、解析、上线、回滚与审计。本文不列具体 parameter_id、默认值、allowed_range 或 YAML schema。本文在主题树中属于横切纪律，是防止参数优化污染结构身份的工程治理方法论。

本篇主要权限层级：H/P。参数系统边界属于 H；具体参数、范围、baseline 与测试口径属于 P。

## 1. 核心结论

第一，参数系统管理的是结构身份不漂移前提下允许调节的自由度 `θ`，而不是策略本体。

第二，参数系统不是第五个 L1 module，不是母结构 component，不是预测系统，也不是动作生成器。

第三，参数应按结构常量、参数化回测变量、主观调节变量等治理边界归册，且归册必须互斥。

第四，baseline parameter set 是 Phase 3 最小可运行输入，不是收益最优声明，也不是实盘推荐参数。

第五，parameter resolver 只输出 runtime parameters，不输出 candidate action、approved action、order instruction 或 governance decision。

## 2. 问题定义

策略系统需要参数，因为触发阈值、窗口、期限分桶、覆盖范围、roll 前置条件、压力识别、执行约束等都不可能全部写死。但参数一旦缺乏治理，会出现两个方向的错误。

一是把结构原则参数化。例如把母结构四要件、coverage 顶层口径、候选与生产区分、md/YAML 权威关系都变成可调参数。二是把参数优化神圣化。例如某组参数在历史样本收益最高，就被写成结构合法性来源。A6 要解决的是：允许自由度存在，但自由度必须被登记、限制、回测、审计和回滚。

## 3. 方法论机制

A6 只处理自由度治理，不处理文档权威或部署 profile；后两者分别由 A7、A8 处理。参数系统处理的是：

参数系统管理 `S(X)` 实现与 `Π(X)` 实现形状中已注册的自由度 `θ`。其中 `X` 是路径空间 / 状态空间中的外部与内部状态；`S(X)` 是异构系统状态响应，`Π(X)` 是标量 payoff functional。参数影响只限于已注册实现，不赋予参数改写 `S/Π` 结构身份的权限。

合法参数治理至少包括：

1. **注册**：参数必须有身份、owner、单位、类型、使用范围、允许范围、版本和 freeze status。
2. **归册**：结构常量、参数化回测变量、主观调节变量必须分清；同一变量不得跨册。
3. **baseline**：给 Phase 3 提供最小可运行参数集，但不代表最优。
4. **resolver**：将参数集解析为运行时参数，且只输出参数。
5. **参数证伪与稳健性测试**：通过参数回测、压力测试、路径置换与反例回放生成 candidate parameter set 与稳健性报告。
6. **Phase 4**：治理上线、回滚、审批、变更留痕与对象身份审查。

参数的合法研究对象包括 `Π(X)` 的实现形状、成本与供血关系、触发条件、约束满足程度、参数稳定性、可复现性和路径依赖度；治理边界只能被检查，不能作为可牺牲权重。非法优化对象包括母结构、`H_identity_target`、顶层 coverage 关系、语义权威关系、阶段权限和治理边界。

coverage by shares 的覆盖关系属于 H 层：`long put 名义覆盖 ≥ k ×（short put 义务仓 + 持有正股）`。其中 `k` 以及长端双翼预算 : 短端供血规模、结构总敞口 : 账户资本等边界数值属于 P 层 `parameter_slot_candidate`，必须进入 A6 参数册治理、版本化与回滚；optimizer 不得删除 H 关系，也不得直接写入生产值。

## 4. 对本策略系统的落点

对 Phase 3 而言，参数系统提供 runtime parameter，使动态执行算法能生成候选，但参数系统本身不生成候选动作。

对 参数证伪与稳健性测试环节 而言，参数回测不应只找最大收益，而应寻找约束违约、路径依赖、压力路径失效和候选参数集的稳健性问题。

对 Phase 4 而言，candidate parameter set 必须经过参数治理才能上线。上线后若产生问题，应能回滚并保留变更日志。

对 Greeks 和 vega 而言，Greeks risk-equivalence、scenario stress、non-netting、vega adjustment 等若成为参数，必须纳入参数册治理，不能临时写入算法。

## 5. 常见误用

第一，把参数系统写成预测系统。参数不能因为“未来大概率如何”而改变结构合法性。

第二，把参数优化写成动作生成。resolver 输出 runtime parameters，不输出 order。

第三，把 baseline 写成最优。baseline 是可运行基线，不是收益最优声明。

第四，把主观调节扩大为结构改写。人工裁量只能在已注册范围内调节，不能新增未注册参数或扩大允许范围。

第五，把结构常量放入可优化参数册。结构身份条件不接受 optimizer 改写。

## 6. 失效条件与反例

A6 失效的反例包括：优化器删除 long put 以提高收益；参数集导致右尾参与缺失却仍上线；同一变量同时归入主观调节册和回测册；resolver 输出 roll candidate；主观判断绕过参数注册表；参数 YAML 新增字段后要求 md 接受。

当参数变化无法说明“它调节的是哪个自由度、是否仍在结构身份内、是否可回滚、是否经过治理”时，该参数不应进入运行系统。

## 7. 可复用表达

```text
参数系统管理的是结构身份内的自由度 θ，而不是策略本体、预测系统或动作生成器。
```

```text
baseline parameter set 是最小可运行输入，不是收益最优声明；candidate parameter set 不等于 production parameter set。
```

```text
parameter resolver 只输出 runtime parameters，不输出候选动作、批准动作、下单指令或治理裁决。
```

# 09｜A7 文档与语义工程

## 0. 文档定位

本文处理的问题是：md、YAML、审计文档、diff、source map、机器可读配置之间的权威关系如何设置。本文不生成 YAML，也不定义具体文件目录规范。本文在主题树中属于工程治理方法论，作用是防止实现层反向污染语义层。

本篇主要权限层级：H。md 语义权威、机器可读化不得反向定义语义，属于文档工程硬约束。

## 1. 核心结论

第一，md 是语义权威源，YAML / SQLite / runtime config 是工程投影。

第二，机器可读化应发生在语义冻结与一致性审计之后，不能先于方法论和 md 裁决。

第三，YAML 不得新增策略语义，不得反向修改 md，不得把工程便利写成结构原则。

第四，diff、审计报告、source map 在写作和修订阶段有价值，但定稿可以保持干净，不必保留全部思考过程。

第五，文档工程本身也是治理系统的一部分，必须能追踪哪些内容是方法论、哪些是字段、哪些是算法、哪些是参数、哪些是部署实例。

## 2. 问题定义

当策略系统逐渐工程化，文档会变成多个层级：方法论 md、结构语义 md、字段文档、算法文档、参数注册表、YAML、profile、审计报告、diff、prompt、PR 评论。若不定义权威关系，最容易发生的错误是：下游格式为了机器可读性、部署便利或局部修复，反向定义上游语义。

例如 YAML 为了类型一致新增字段，profile 为了账户适配改变 core，算法为了实现方便合并阶段权限，参数表为了回测方便新增可优化结构常量。这些都不是技术细节，而是语义污染。

## 3. 方法论机制

文档与语义工程应按权威层级组织：

```text
方法论 / 宪法层 md
  ↓
结构语义 / 模块 / workflow md
  ↓
字段 / 算法 / 参数 md
  ↓
机器可读 YAML / SQLite / config
  ↓
runtime binding / deployment instance
```

上游定义语义，下游投影语义。下游可以暴露上游缺口，形成修订请求，但不能自行改写上游。

机器可读化流程应为：

```text
md 升级
  ↓
md 一致性审计
  ↓
YAML 生成
  ↓
YAML 与 md 映射审计
  ↓
部署绑定
```

文档定稿应追求稳定清晰，而不是保留所有思考痕迹。source map 可作为独立审计附件保留，用于追踪来源与修订依据，但不进入正式正文。冲突历史可在版本治理需要时另行记录，不进入方法论正文。

## 4. 对本策略系统的落点

对本方法论文档集而言，来源映射应作为独立审计附件保留，不进入正式正文。

对后续字段和算法升级而言，不能让现有旧字段、旧算法反向约束新方法论。应先冻结方法论，再定义字段 / 算法重构任务。

对 YAML 而言，YAML 只能表达已冻结 md 的机器可读投影。例如参数注册、baseline、validation、profile binding 都应来自 md，不得由 YAML 创造新业务语义。

对 Codex / Claude / GPT workflow 而言，prompt 应明确本轮是方法论写作、字段修订、算法重构、YAML 生成还是审计，避免一次任务跨越多个权威层级。

## 5. 常见误用

第一，把 YAML 写成权威文档。机器可读不等于语义权威。

第二，把审计报告写成正文。审计结果用于修订，不一定进入最终方法论文档。

第三，把 diff 历史长期保留在正文中，导致定稿像修订说明而不是方法论文章。

第四，把字段文档当作方法论主源。字段是下游操作单元，不应反向定义上位原则。

第五，把 prompt 当作长期知识资产。prompt 是执行接口，方法论文档才是可复用资产。

## 6. 失效条件与反例

A7 失效的反例包括：YAML 中出现 md 没有定义的策略规则；profile 增加账户规模限制后改写 core；算法文档为了实现方便将 Phase 2 与 Phase 4 合并；参数 patch 改变结构常量语义；定稿中保留大量旧版本冲突过程导致读者无法识别当前口径。

当系统无法回答“这条语义的权威来源是哪份 md，机器文件是否只是投影”时，文档工程失效。

## 7. 可复用表达

```text
md 是语义权威源，YAML 是工程投影；机器可读化不得反向定义策略语义。
```

```text
先冻结语义，再生成机器可读配置；先做 md 一致性审计，再做 YAML 映射审计。
```

```text
定稿文档应保留当前稳定口径，不必保留所有旧冲突和修正过程。
```

# 10｜A8 部署与 Profile 工程

## 0. 文档定位

本文处理的问题是：strategy core、machine-readable core、L0 config profile、underlying profile、account profile、deployment profile、runtime binding 之间如何分离。本文不定义具体 QQQ / SPY / IBKR 配置，也不生成 profile YAML。本文在主题树中属于工程治理方法论，作用是防止部署实例改写策略核心。

本篇主要权限层级：H/P。core/profile 边界属于 H；具体 profile 内容与 runtime binding 模板属于 P。

## 1. 核心结论

第一，strategy core 定义策略本体与参数系统，profile 只做部署实例化。

第二，底层标的、base currency、broker、账户规模、live / paper、最大 NAV 使用比例、期权链配置、流动性假设等不应写死进 core。

第三，deployment profile 是一次部署绑定，不是新的策略语义来源。

第四，多标的扩展必须经过 object identity review，不能因为工具相似就默认同一策略。

第五，runtime binding 只能把 core、参数集、L0 配置、标的、账户和运行模式绑定为一次运行，不得改变上游定义。

## 2. 问题定义

策略从研究走向实盘时，必然遇到部署差异：不同标的、账户规模、broker、期权流动性、合约乘数、交易日历、保证金规则、paper / live 环境。如果这些差异直接写入 core，策略本体会被部署细节污染；如果完全忽略这些差异，策略又无法实际运行。

A8 的方法论任务是把“策略是谁”和“这次在哪里、用什么账户、交易什么标的、以什么配置运行”分开。前者是 core，后者是 profile / deployment / runtime binding。

## 3. 方法论机制

推荐层级为：

```text
strategy_core
  ↓
machine_readable_core
  ↓
l0_config_profiles
underlying_profiles
account_profiles
  ↓
deployment_profiles
  ↓
runtime_binding
```

`strategy_core` 保存方法论、结构语义、参数系统和治理边界。`machine_readable_core` 是 core 的 YAML / SQLite 投影。`l0_config_profile` 实例化全局分桶、窗口、resolver 规则等配置。`underlying_profile` 描述标的、期权市场、合约乘数、交易日历、结算与流动性适配。`account_profile` 描述账户、broker、资金约束、权限与执行环境。`deployment_profile` 将 core、参数集、L0 配置、标的和账户绑定为一次部署。`runtime_binding` 是实际运行时的绑定状态。

关键纪律是：profile 可以使 core 落地，但不能改写 core。若某个标的或账户约束导致母结构四要件无法满足，不能通过 profile 静默降级，而应触发 object identity review。

## 4. 对本策略系统的落点

对 QQQ 主版本而言，QQQ、USD、IBKR、账户规模、目标仓位、现金保留比例、期权链流动性等应放在 profile 层，而不是策略本体。

对多标的扩展而言，SPY、QQQ、TQQQ、SMH、IWM 等不能只因都有期权链就被视为等价部署。需要检查底层资产属性、波动率结构、流动性、合约规则、策略适配性与对象身份。

对参数系统而言，profile 中的 L0 配置实例化值应绑定到已注册参数或配置对象，不应创造新的未注册自由度。

对实盘执行而言，一次运行应记录使用哪个 core、哪个 parameter set、哪个 L0 profile、哪个 underlying profile、哪个 account profile、哪个 runtime mode，以便审计和回滚。

## 5. 常见误用

第一，把标的写进 core。当前主应用可以聚焦 QQQ / NDX，但具体部署值不应混入参数注册表本体。

第二，把账户限制改写成策略原则。例如账户小所以取消长端保护，不能仍称为同一 core 的部署实例。

第三，把 profile 当成策略扩展。profile 是绑定，不是新策略。

第四，把多标的扩展当成复制文件。不同标的需要 object identity review。

第五，把 paper trading 与 live trading 的差异藏在 runtime 中而不审计。

## 6. 失效条件与反例

A8 失效的反例包括：underlying_id 写死进 parameter registry；account size 直接改变母结构比例而不留痕；TQQQ profile 复用 QQQ core 但未检查杠杆 ETF 路径衰减；broker 限制导致无法执行 long wings 但仍上线；deployment profile 修改 resolver 输出边界。

当一个部署实例无法说明其绑定的 core、参数集、标的、账户和运行模式，或当它为了落地而改变 core 语义时，A8 失效。

## 7. 可复用表达

```text
profile 负责实例化和绑定 core，不负责定义 core；deployment 是一次运行绑定，不是新的策略语义来源。
```

```text
底层标的、账户、broker、运行模式和账户规模属于部署层，不应写死进策略本体。
```

```text
多标的扩展不是复制配置文件，而是一次 object identity review。
```

# 11｜B3 功能迁移与动作语义

## 0. 文档定位

本文处理的问题是：对冲、置换、roll、partial monetization、局部风险改形等动作在本策略中到底承担什么功能。本文不写具体触发阈值、执行价选择、order routing 或交易指令。本文在主题树中属于运行脊柱中的操作语义，是连接对象身份、候选生成和治理裁决的动作语言。

本篇主要权限层级：P。动作语义可以随工具演化，但动作候选必须进入 B2 权限链。

## 1. 核心结论

第一，动作不是目的，动作是功能迁移、风险改形或账本重分配的工具。

第二，对冲在本策略中不是消灭风险，而是把不愿裸露承受的风险改写成可承受、可供血、可管理或在关键路径中更有利的形状。

第三，roll 不是展期，而是功能迁移；判断 roll 合法性要看它是否维护 optionality、Gamma 中心、高阶凸性和功能承担关系。

第四，置换不是守住某张合约，而是守住结构功能，并允许承担者迁移。

第五，任何动作都必须先作为 candidate 进入治理；动作语义清楚，不等于动作被批准。

## 2. 问题定义

如果没有统一动作语义，策略执行会退化成机械规则：Delta 到某值就 hedge，DTE 到某天就 roll，盈利到某比例就卖，VIX 到某水平就切换。这种规则看似可执行，却容易把局部 proxy 或工具动作写成上位目标。

波动率凸性策略需要动态维护，但动态不等于频繁操作。每个动作必须回答：它维护了什么结构功能，迁移了哪个承担者，改写了哪类风险，是否破坏母结构四要件，是否仍通过治理审查。

## 3. 方法论机制

本策略的动作语言可分为几类：

1. **对冲 = 风险改形**。A 版硬 Delta 对冲只处理瞬时线性暴露，容易破坏有利 gamma；B 版 Greeks 对冲处理局部风险形状；C 版路径对冲处理路径响应；D 版结构对冲维护母结构收益函数形状。本策略追求 D 版，允许 B/C 作为执行手段，避免把 A 版写成上位原则。

2. **置换 = 功能接力**。同 Greek 置换、不同 Greeks 间置换、载体置换、路径置换、账本置换都不是为了保留原合约，而是为了让结构功能由更合适的承担者接续。

3. **roll = 功能迁移**。roll 的目的不是延长期限，而是维护 optionality、Gamma 中心、高阶凸性、账本关系和功能承担。

4. **partial monetization = 激活后期的有限兑现与账本 / 风险响应再分配**。partial monetization 不是简单止盈或收益最大化动作，而是在反脆弱激活生命周期后期，在不破坏剩余保护与结构身份前提下，对已激活凸性收益进行有限兑现，并完成账本与风险响应再分配。

5. **局部风险改形 = 在不改变母结构身份前提下调整局部暴露形状**。它服务本体，不定义本体。

## 4. 对本策略系统的落点

对 Phase 3 而言，动作语义用于生成 candidate。一个候选动作必须说明动作母类、目标功能、输入事实、诊断依据、预期功能迁移、可能破坏的约束和需要进入 Phase 4 的检查项。

候选动作模板如下：

```yaml
candidate_action_template:
  action_family: hedge / roll / replacement / partial_monetization / risk_reshape
  target_function: 该动作维护或迁移的结构功能
  phase2_inputs: 所需事实、账本、raw exposure、coverage、funding 状态
  phase3_diagnostic: 触发该候选的诊断理由
  expected_function_migration: 功能承担者如何迁移
  potential_constraint_impact: 可能影响哪些 H/P 约束
  phase4_required_checks: 进入治理前必须检查的 constraint stack 项目
  post_action_check: 执行后需要重新计算的合法性项目
```

对 Phase 4 而言，治理审查不应只问动作是否“看起来合理”，而应问：动作后 long put / long call / short funding / tenor mismatch / roll optionality 是否仍满足对象身份，coverage、funding、vega、账本和 profile 边界是否仍守约。

对文档与 prompt 而言，后续任何执行类 prompt 都应避免“直接下单”式表达，而应写成“生成候选动作并进入治理审查”。

对 Greeks 而言，Greeks-triggered action 只是 candidate。Gamma、Vega、Delta、Theta 的变化可以作为 Greeks 观察提示动作需要，但不直接批准动作。

## 5. 常见误用

第一，把 roll 当展期。展期只是时间延长，roll 在本体系中必须服务功能迁移。

第二，把 hedge 当风险消灭。对冲只是风险改形，错误对冲可能破坏凸性。

第三，把 partial monetization 当止盈。若兑现导致尾部保护或 long vega 不足，可能破坏结构身份。

第四，把动作触发条件当动作合法性。触发只生成候选，合法性由治理决定。

第五，把局部风险改形写成新母结构。工具实现层不得篡位本体。

## 6. 失效条件与反例

B3 失效的反例包括：硬 Delta 对冲把 long gamma 结构刷平；roll 后保护腿离开有效激活区；盈利后卖出 long put 导致左尾保护缺失；为了降低 long-end premium bleed / theta decay cost 删除 long call 右尾；局部 overlay 盈利后被写成主策略；路径置换依赖主观预测而不是结构响应改形。

当动作无法说明其维护的结构功能，或动作执行后无法通过对象身份与约束审查时，该动作语义不成立。

## 7. 可复用表达

```text
对冲不是消灭风险，而是风险改形；roll 不是展期，而是功能迁移；置换不是守住合约，而是守住结构功能。
```

```text
动作语义清楚，只说明它可以成为候选；动作是否被批准，必须进入 Phase 4 治理裁决。
```

```text
任何执行动作都必须回答：它维护什么功能、迁移什么承担者、改写什么风险、是否破坏对象身份。
```

# 12｜C1 Greeks 风险语言

## 0. 文档定位

本文处理的问题是：Delta、Gamma、Vega、Theta 及高阶 Greeks 在波动率凸性结构中如何观察、display、诊断、聚合和治理。本文不定义具体 Greeks 字段清单、阈值、算法实现或交易规则。本文在主题树中属于工具层操作语言，服务于 option-centric 结构的风险响应表达。

本篇主要权限层级：P/H。Greeks 作为风险语言属于 P；Greeks 不定义结构、不替代治理裁决属于 H。

## 1. 核心结论

第一，Greeks 不定义结构；Greeks 描述结构的路径响应。

第二，Greeks 需要独立观察、独立 display、独立诊断，但不应成为第五个 L1 module，也不应成为母结构 component。

第三，Greeks raw exposure 属于事实；Greeks by tenor / moneyness / expiry 属于 proxy；Greeks diagnostic 属于 Phase 3；Greeks-triggered action 只是 candidate；Greeks-related legality 属于 Phase 4。

第四，Greeks 不得以简单 scalar netting 方式跨 tenor、call/put、leg_type、moneyness、side 直接相加相减后用于治理裁决。

第五，任何 aggregate Greek metric 必须声明 aggregation scope、risk-equivalence rule、scenario assumption 和 allowed usage。

## 2. 问题定义

期权结构如果不观察 Greeks，就无法理解局部路径响应；但如果把 Greeks 提升为结构本体，就会把策略退化为指标管理。特别是 vega、gamma、theta 等暴露，跨期限、跨 moneyness、跨 put/call、跨 long/short 后，经济含义并不相同。一个简单净值可能在显示上方便，却在治理上危险。

C1 要解决的是：如何让 Greeks 成为高质量风险语言，而不是结构裁决器。

## 3. 方法论机制

C1 不重复 A5 的一般 proxy 治理，只处理 Greeks 作为 option-centric 风险语言时的特殊要求。

### 3.1 度量形态基准：六态

Vega / Greeks 的 canonical 度量形态基准为六态：

| 度量形态 | 方法论含义 | 默认 Phase 标注边界 |
|---|---|---|
| raw | 原始持仓与风险节点暴露 | Phase 2 fact |
| tenor | 按期限分段表达 | Phase 2 observation；可作为 Phase 3 input |
| forward-segmented | 按远期区段拆分表达 | Phase 2 derived observation；可作为 Phase 3 input |
| surface | 按波动率曲面坐标表达 | Phase 2 observation / Phase 3 diagnostic input |
| grid | 按价格—波动率—期限网格表达 | Phase 2 observation / Phase 3 diagnostic input |
| scenario-stressed | 在声明情景下重估 | Phase 3 diagnostic / Phase 4 governance input |

六态是“度量形态枚举”，Phase 是“运行权限轴”。每个形态实例必须独立标注来源 Phase 与允许用途；不得把六态与 Phase 2/3/4 合并为同一计数体系。字段、算法与 canonical schema 留待 B-2 / 下游工程文档。

### 3.2 Phase 权限角色链

权限角色链为：

```text
Phase 2：facts / observations
Phase 3：diagnostics / risk-equivalent interpretation / candidate input
Phase 4：Greeks-related governance input
```

下表描述权限角色，不构成另一套“六态”计数：

| 权限角色 | 所属权限层 | 允许用途 | 禁止用途 |
|---|---|---|---|
| raw Greeks | Phase 2 | 按 lot / leg / tenor / side / option type / moneyness / expiry 保留原始暴露 | 直接推出动作或治理裁决 |
| proxy Greeks | Phase 2 / Phase 3 输入 | 压缩、分桶、display、辅助诊断 | 替代完整对象状态或 constraint stack |
| diagnostic Greeks | Phase 3 | 解释 gamma center、vega concentration、theta burn、wing dullness 等状态 | 批准动作或下单 |
| risk-equivalent Greeks | Phase 3 / Phase 4 输入 | 在声明等价规则、聚合范围与适用假设后辅助诊断或治理 | 未声明等价规则时作为最终口径 |
| scenario-stressed Greeks | Phase 3 / Phase 4 输入 | 在价格、波动率、skew、term structure、liquidity 情景下重估压力响应 | 用静态粗汇总替代压力情景 |
| governance input | Phase 4 | 进入 constraint stack，辅助 approval / block / manual review | 替代 governance decision 本身 |

基础管理单位不是 total Greek，而是 option surface node。一个 node 至少应保留 lot_id、leg_type、side、option_type、expiry、tenor bucket、strike、moneyness bucket、liquidity bucket 等信息。只有先保留 node / bucket 层表达，后续 aggregate 才有可解释性。

Greeks display 应成为独立 dashboard，例如 Risk Response Dashboard 或 Greeks Exposure & Convexity Dashboard。它用于观察结构响应，不用于直接批准动作。

Non-netting principle 是 C1 的核心纪律。不能直接把所有 vega、gamma、theta、delta 加总后作为最终管理口径。front tenor vega 与 back tenor vega 不等价，short put gamma 与 short call gamma 不等价，ATM gamma 与 wing gamma 不等价，near-expiry theta 与 long-dated theta 不等价，put wing vol exposure 与 call wing vol exposure 也不等价。

## 4. 对本策略系统的落点

对 Phase 2 而言，系统可以输出 raw Greeks by lot、by leg、by tenor、by moneyness、by option type、by side，以及粗略 parallel summary，但这些不是治理裁决。

对 Phase 3 而言，Greeks Observation 可以诊断 gamma center 是否偏离、vega 承担是否集中、theta burn 是否不可持续、short gamma 是否过度、long wing 是否钝化，并据此生成 candidate。

对 Phase 4 而言，Greeks 可成为 constraint stack 的输入，但不得替代 coverage by shares、premium-based funding relation、对象身份和 post-action legality。尤其不能用未声明等价规则和压力情景的 vega 汇总值替代完整期限错配治理。

对 B3 动作语义而言，Greeks-triggered action 必须写成 candidate，例如 roll candidate、risk reshape candidate、reduce short candidate、rebuild long wing candidate，而不是直接 action。

## 5. 常见误用

第一，把 total Greek 当最终风险。total 值可能掩盖期限、行权价、put/call、long/short 的结构差异。

第二，把 vega 汇总值当结构合法性。raw vega 只能作为观察和输入，治理需要等价规则、聚合范围和情景假设。

第三，把 Greeks dashboard 当执行面板。display 不等于 approval。

第四，把 Greeks 管理写成第五模块。Greeks 是横切观察与诊断语言，不是主模块。

第五，把 Greeks 替代 coverage 或 funding。LP / LC 的顶层覆盖口径不能被 Greeks 替换；融资可持续性也不能被 Theta proxy 或短端 premium income 直接替代。

## 6. 失效条件与反例

C1 失效的反例包括：未声明等价规则的 gamma 汇总值为正就认为左尾安全；未声明压力情景的 vega 汇总值为正就认为期限错配合法；短端虚值权利金收入大于 long-end premium bleed / theta decay cost 就认为 funding 可持续；dashboard 显示风险降低就批准 partial monetization；跨 put/call、tenor、moneyness 的 scalar netting 未声明规则却用于治理。

当某个 Greeks 指标无法说明聚合范围、等价规则、情景假设和允许用途时，它只能作为粗观察，不能进入诊断、候选批准或治理裁决。

## 7. 可复用表达

```text
Greeks 不定义结构；Greeks 描述结构的路径响应。
```

```text
Greeks 应被 display 成独立风险响应仪表盘，被管理成 Phase 3 诊断单元，被治理成 Phase 4 审计对象，但不能成为第五模块或母结构 component。
```

```text
任何 aggregate Greek metric 必须声明 aggregation scope、risk-equivalence rule、scenario assumption 和 allowed usage；否则只能作为 rough observation。
```
