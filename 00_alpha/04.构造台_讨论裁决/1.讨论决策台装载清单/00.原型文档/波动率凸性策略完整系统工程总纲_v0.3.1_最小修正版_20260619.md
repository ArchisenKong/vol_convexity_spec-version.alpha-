# 0. 文档定位、适用范围与规范语言

## 0.1 总纲的工程宪章与元治理定位

本总纲定位为：

> **波动率凸性策略完整系统的工程总纲、规范装配宪章与全生命周期控制框架。**

总纲属于工程组织权威，不重新定义策略方法论、策略身份、母结构、Phase 权限、Greeks 分层、volatility positioning、candidate、governance 或具体执行规则。

总纲的职责是：将已经批准的策略语义和专业 Taxonomy，装配成一条能够稳定下沉到字段、算法、参数、数据、模型、Workflow、状态机、代码、测试、部署、运行证据、维护、迁移和退役的完整工程链。

## 0.2 适用范围

本总纲适用于波动率凸性、option-centric、路径响应型量化策略系统在以下活动中的工程组织：

```text
研究
回测
Replay
Paper
Shadow
Limited Live
Production Live
监控
维护
迁移
升级
退役
```

本总纲作为一般性工程总纲，不记录特定项目阶段、当前完成度、既有文档整改状态、历史任务批次或具体推进顺序。

## 0.3 非目标

本总纲不得承担以下内容：

```text
重新定义策略身份；
重新定义母结构；
重新解释 H/P/W；
重新定义 Phase 权限；
重新定义 volatility positioning；
重新定义 Greeks 分层；
重新定义 candidate / governance；
直接冻结生产字段；
直接定义算法步骤；
直接确定参数值；
直接生成生产 YAML；
直接规定具体交易动作；
直接成为自动执行规则。
```

对上述内容，本总纲只负责：

```text
引用 canonical source
→ 规定下沉接口
→ 规定验证要求
→ 规定禁止越权
```

## 0.4 MUST / SHOULD / MAY

本总纲采用长期有效、无项目状态的规范性表达。

```text
MUST：强制要求；不满足即不得通过对应 Gate。
SHOULD：原则性要求；如不采用，必须记录替代控制和等效性依据。
MAY：允许项；不得由允许项反推为默认义务或自动授权。
```

凡涉及策略身份、权限链、禁止自动化、字段冻结、参数上线、执行授权和 Runtime Evidence 的要求，除非明确标注为 SHOULD 或 MAY，否则按 MUST 解释。

## 0.5 总纲与子规范的颗粒度边界

总纲负责定义：

```text
某一专业域必须存在；
该专业域的职责边界；
该专业域需要形成哪些 canonical 子规范；
该专业域必须经过哪些 Gate；
该专业域应留下哪些 Artifact 与 Runtime Evidence；
该专业域与其他专业域的依赖方向。
```

总纲不负责直接展开：

```text
具体字段名；
字段类型；
数据库表；
API endpoint；
算法步骤；
模型公式细节；
参数数值；
YAML key；
生产部署配置；
交易动作触发条件。
```

这些内容必须进入对应 canonical 专业子规范。

## 0.6 总纲自身版本与变更规则

总纲自身变更必须保留：

```text
版本号；
变更原因；
影响范围；
对应 Change Request；
受影响章节；
受影响子规范；
diff；
批准记录；
回滚路径。
```

若总纲程序要求与语义权威冲突，总纲不得覆盖语义；必须提交 Change Request，并在裁决前保持 fail-closed 或既有稳定版本。

# 1. 语义权威、Canonical Source 与 Change Request

## 1.1 Semantic Authority

语义权威回答：

```text
系统是什么；
系统维护什么对象；
哪些语义是合法的；
哪些行为被禁止；
不同 Phase 具有什么权限。
```

方法论、对象身份、母结构、Phase 权限、H/P/W 和策略含义由已批准 Semantic Authority 定义。总纲不得反向改写。

## 1.2 策略身份与对象身份指针

本系统的工程对象必须指向已经批准的策略语义与对象身份。工程实现只能承接该身份，不得通过字段、参数、profile、YAML、代码或 runtime binding 改写 strategy core。

## 1.3 Canonical Source Matrix

系统必须为以下对象维护 canonical source：

| 对象 | canonical source |
|---|---|
| 策略身份、母结构、Phase、H/P/W 及方法论含义 | Semantic Authority |
| 对象分类、可下沉性、权限标签、Forbidden Automation / Override | 已批准 Taxonomy |
| Artifact、Stage-Gate、证据、流程和工程组织要求 | 工程总纲 |
| Field、Algorithm、Model、Parameter、Schema 等正式工程合同 | 对应 canonical 专业子规范 |
| 系统实际执行、事件和状态事实 | 受控 Code / Runtime Evidence |

任何 canonical source 必须带有版本、哈希或等效 lineage 标识。

## 1.4 语义权威与工程组织权威

工程组织权威回答：

```text
这些语义如何被组织；
如何被下沉；
如何被实现；
如何被验证；
如何在不同环境中运行；
如何维护、迁移、回滚和退役。
```

总纲属于工程组织权威。总纲不得重新定义语义权威，但可以规定所有下游规范和实现必须如何承接语义权威。

## 1.5 语义—实现下沉链

```text
Semantic Authority
策略方法论、对象身份、权限和母结构
        ↓
Taxonomy Bridge
专业分类、对象边界和安全下沉关系
        ↓
Engineering Specification
Field / Algorithm / Parameter / Data / Model / Workflow Contract
        ↓
Machine-readable Contract
Schema / YAML / API / State Machine / Database Constraint
        ↓
Implementation
Code / Test / Build / Deployment
        ↓
Runtime Evidence
Event / State / Decision / Order / Fill / Audit / Incident
```

## 1.6 总纲元治理覆盖关系

总纲位于整条语义—实现—运行链之上的元治理层，负责规定各层的职责、依赖、Artifact、Gate、证据和反馈机制；它不取代任何一层的 canonical 定义，也不作为该链中的普通业务节点。

```text
                 完整系统工程总纲
                         │
       ┌─────────────────┼─────────────────┐
       ↓                 ↓                 ↓
Semantic / Taxonomy   Engineering      Runtime / Change
权威与下沉治理        实现与验证治理     运行与演化治理
```

## 1.7 单向依赖和禁止反向改写

依赖方向必须保持为：

```text
Semantic Authority
→ Taxonomy
→ Engineering Specification
→ Machine-readable Contract
→ Implementation
→ Runtime Evidence
```

禁止：

```text
字段擅自增加策略含义；
算法越过权限边界；
参数隐藏在代码中；
diagnostic 直接变成 order；
candidate 绕过 governance；
研究结果未经校准进入实盘；
Bug 只做局部修复；
新版本无法解释旧持仓和旧状态。
```

## 1.8 上游勘误与 Change Request

若下游实现、运行证据、反例或 Incident 暴露上游语义问题，必须通过 Change Request 回到上游裁决，不得由代码、参数或 profile 直接修补语义。

Change Request 至少记录：

```text
冲突对象；
上游引用版本；
下游证据；
影响范围；
建议处理；
批准记录；
受影响 Artifact；
回滚路径。
```

## 1.9 权威域与冲突裁决矩阵

| 冲突对象 | 最终权威与处理方式 |
|---|---|
| 策略身份、母结构、Phase、H/P/W 及方法论含义 | 以 Semantic Authority 为准 |
| 对象分类、可下沉性、权限标签、Forbidden Automation / Override | 以已批准 Taxonomy 为准 |
| Artifact、Stage-Gate、证据、流程和工程组织要求 | 以工程总纲为准 |
| Field、Algorithm、Model、Parameter、Schema 等正式工程合同 | 以对应 canonical 专业子规范为准 |
| 系统实际执行、事件和状态事实 | 以受控 Code / Runtime Evidence 为事实依据，但不得据此反向改写上游语义 |
| 实现与语义权威冲突 | 将实现判定为 Defect，阻断或回退，不以现行代码作为语义依据 |
| 总纲程序要求与语义权威冲突 | 总纲不得覆盖语义；提交 Change Request，并在裁决前保持 fail-closed 或既有稳定版本 |

任何权威冲突都必须留下冲突对象、引用版本、裁决依据、批准记录和受影响 Artifact。

# 2. Taxonomy 与安全下沉治理

## 2.1 Taxonomy Bridge

Taxonomy Bridge 是方法论资产进入工程资产前的安全下沉层。它决定：

```text
哪些概念可以下沉；
可以下沉到哪里；
以什么权限下沉；
哪些必须保留为人工治理；
哪些必须禁止机器化或自动化。
```

Bridge 不是字段冻结稿、算法实现稿、YAML schema、参数注册表、runtime binding instance 或自动交易规则。

## 2.2 Canonical 家与对象边界

Taxonomy 必须为每一类对象指定 canonical 家与对象边界。同一概念只能在唯一 canonical 家中定义；其他文档只能引用、检验或承接，不得重复定义或改写。

## 2.3 Phase / Authority 标注

所有可下沉对象必须带有 Phase 与 Authority 标注：

```text
Phase 2：事实计算、账本表达、raw exposure 与 raw observation。
Phase 3：诊断、候选生成、修复建议、人工审查触发。
Phase 4：constraint stack、治理裁决、approval / block / manual review / rollback / post-action audit。
```

candidate 不等于 approved action；governance input 不等于 governance decision。

## 2.4 Field / Algorithm / Parameter / Governance 准入

Field、Algorithm、Parameter、Governance 的下沉必须满足：

```text
已存在上游 Semantic Pointer；
已通过 Taxonomy Bridge 准入；
已明确对象权限；
已声明不变量与禁止项；
已绑定对应子规范；
已进入相应 Gate。
```

Bridge 只决定准入和边界，不直接生成实现稿。

## 2.5 Forbidden Automation / Forbidden Override

必须显式维护 Forbidden Automation 与 Forbidden Override 注册表。至少禁止：

```text
diagnostic → order；
candidate → order；
post-action audit → next trade trigger；
profile / YAML / runtime → strategy core override；
单一 Greek / proxy → governance decision；
研究参数 → production parameter set；
异常 override → 永久规则。
```

## 2.6 Downstream Gate

Taxonomy-to-Engineering 进入下游前必须通过 Downstream Gate。Gate 至少验证：

```text
canonical 家是否唯一；
对象边界是否清楚；
权限标注是否完整；
禁止自动化是否落实；
是否存在误字段化、误算法化、误 YAML 化、误自动交易化；
下游子规范是否接收正确。
```

# 3. 系统目标、工程质量属性与非功能性要求

## 3.1 稳定性

系统必须在数据缺失、行情延迟、订单未知、partial fill、Broker 重连、人工干预、参数回滚、版本迁移和 Incident 恢复时保持受控状态。稳定性依赖幂等、事务、恢复、重放、对账、回滚和 fail-closed 机制。

## 3.2 一致性

系统必须保证语义一致、字段一致、算法一致、参数一致、状态一致和跨环境一致。代码、测试、数据库、Schema、YAML 和 runtime evidence 不得形成与上游语义冲突的第二权威。

## 3.3 完整性

完整性要求每一个必要专业域都有归属，每一个阶段都有正式承接，每一个对象都有权威来源，每一个实现都有验证，每一个运行结果都有证据。

## 3.4 无缝衔接

系统必须通过 Bridge、Artifact、Gate 和 Lineage 保持从 Semantic Authority 到 Runtime Evidence 的连续性。任何系统问题都应能定位到：

```text
所属专业域；
代码前、代码中或代码后；
运行或验证模式；
定义它的规范层；
产生的标准 Artifact；
验证它的 Gate；
最终留下的 Runtime Evidence。
```

## 3.5 非功能性质量属性

下游专业规范和 Deployment Profile 必须显式定义非功能性约束，总纲本身不冻结具体数值。最低覆盖范围包括：

```text
数据最大允许新鲜度；
计算和决策延迟预算；
订单提交前最终快照重读与复核时限；
事件积压与处理吞吐边界；
系统可用性与降级模式；
RTO / RPO；
存储容量与增长预算；
研究任务和生产任务的资源隔离；
日志、审计证据和研究 Artifact 保留期；
Replay、恢复和对账的时间预算；
监控覆盖率与告警可达性；
备份验证与恢复演练频率。
```

## 3.6 Objective–Control–Artifact–Gate–Evidence Matrix

| 目标 | 控制机制 | 标准 Artifact | Gate | Runtime Evidence |
|---|---|---|---|---|
| 稳定性 | 幂等、事务、恢复、重放、对账、回滚 | Failure Contract / Recovery Plan | G6–G12 | Replay report / Reconciliation diff |
| 语义一致性 | Canonical pointer、禁止反向改写 | Traceability Matrix | G0–G8 | Requirement coverage |
| 跨模式一致性 | 同一 Domain Kernel、显式 Adapter | Environment Difference Matrix | G3–G10B | Replay / Shadow comparison |
| 状态一致性 | Fill-based rebuild、账本对账 | State Reconstruction Spec | G3–G12 | Position / Ledger diff |
| 完整性 | 正常路径、异常路径、迁移、退役 | Lifecycle Coverage Matrix | G6–G12、MG、RG | Audit bundle |
| 无缝衔接 | Bridge、Artifact、Gate、Lineage | Artifact Manifest / System Coverage Matrix | 全阶段 | End-to-end trace |
| 版本连续性 | Compatibility、Migration、Parallel Run | Migration Plan | CG、MG | Migration report |
| 退役可解释性 | Deprecation、归档、历史解释 | Retirement Plan | RG | Retirement evidence |

# 4. 多维组织模型与总体元架构

## 4.1 治理覆盖模型

本系统不采用单线目录组织，而采用多维治理覆盖模型：

```text
专业控制域轴
× 工程生命周期轴
× 运行与验证模式轴
× 系统平面矩阵
× Profile / Applicability 标注
```

## 4.2 专业控制域轴

总纲以专业控制域作为主目录骨架。专业控制域包括：

```text
A. 语义权威、Canonical Source 与 Change Request
B. Taxonomy 与安全下沉治理
C. 系统架构、系统平面与工具职责
D. 数据架构、时间语义与数据治理
E. 领域对象、字段与工程合同
F. 模型、参数与 Research-to-Live 治理
G. Workflow、事件、状态机与执行治理
H. 质量、验证、反例与 Observability
I. Release、Change、Migration、Rollback 与 Retirement
J. 权限、安全、角色与禁止自动化
K. Traceability、Lineage、Artifact 与文档治理
```

## 4.3 工程生命周期轴

工程生命周期轴为：

```text
代码前
→ 代码中
→ 代码后
```

它回答什么时候形成规范、什么时候允许编码、什么时候验证发布和运行、什么证据允许进入下一阶段。

## 4.4 Exploratory Research Backtest 与 Production-path Historical Validation

必须区分：

```text
Exploratory Research Backtest：研究假设、参数区间、反例路径、敏感性和可行性，不等于生产路径证明。
Production-path Historical Validation：使用受控工程实现、受控参数、受控事件合同和生产路径逻辑进行历史验证。
```

不得使用未限定的 Historical Backtest 混合指代上述两类验证。

## 4.5 Runtime Mode Contract

每一种运行或验证模式都必须定义 Runtime Mode Contract，包括：

```text
允许的输入；
禁止的输入；
状态写入权限；
外部副作用；
参数来源；
证据输出；
晋升条件；
回退条件。
```

覆盖模式包括：

```text
Exploratory Research Backtest
Production-path Historical Validation
Deterministic Replay
Paper
Shadow
Limited Live
Production Live
```

## 4.6 Lifecycle Planes

Lifecycle Planes 描述系统活动发生在哪一类生命周期平面：

```text
Research
Engineering
Operations
```

Research、Engineering 和 Operations 不是运行模式，不能与 Backtest、Replay、Paper、Shadow、Live 作为互斥环境并列。

## 4.7 Functional Planes

Functional Planes 描述系统能力的功能分区：

```text
Data Plane
Domain / State Plane
Decision / Governance Plane
Execution Plane
Observability Plane
Control / Release Plane
Human Interaction Plane
```

## 4.8 System Plane Matrix

系统必须形成 Lifecycle Plane × Functional Plane Matrix，用于说明每个专业对象在哪个平面定义、验证、运行、观察和留证。

## 4.9 Normative Level × Applicable Profile × Applicability Disposition

每项要求必须采用三元正交标注：

```text
Normative Level
× Applicable Profile
× Applicability Disposition
```

Not Applicable 只表示适用性处置，不得作为 Normative Level。

## 4.10 Domain Kernel 与 Adapter 边界

Shared Domain Kernel 必须尽可能共享以下对象和逻辑：

```text
Ledger
Structure State
Mother-Structure Identity
Volatility Positioning
Portfolio Greeks
Trading Concepts Residual Risk
Coupling
Scenario
Diagnostic
Candidate
Governance
Post-action Audit
Parameter Binding
State Transition
```

Domain Kernel 不应直接依赖 IBKR 原生对象、QuantConnect 原生对象、Excel、Streamlit、PostgreSQL 具体实现、系统当前时间或真实 Broker Writer。

## 4.11 环境差异注入规则

环境差异只能存在于 Adapter 与 Model：

```text
Clock
Market Data Adapter
Account / Position Adapter
Broker Adapter
Execution Model
Fee Model
Slippage Model
Liquidity Model
Assignment / Expiry Model
Margin Model
```

禁止在不同环境中重写 diagnostic、candidate、账本、参数语义或 governance 主链。

# 5. Traceability、Lineage、Artifact 与文档治理

## 5.1 规范和制品层级

系统制品层级为：

```text
Semantic Authority
→ Taxonomy Bridge
→ Engineering Specification
→ Machine-readable Contract
→ Implementation
→ Runtime Evidence
```

每一层必须保留上游指针和下游消费关系。

## 5.2 Artifact Taxonomy

标准 Artifact 至少包括：

```text
Semantic Pointer
Taxonomy Decision
Engineering Contract
Machine-readable Schema
Parameter Registry
Runtime Binding
Test Evidence
Replay Report
Release Artifact
Migration Plan
Incident Report
Audit Bundle
Retirement Evidence
```

## 5.3 Artifact Lifecycle

Artifact 生命周期必须覆盖：

```text
draft
reviewed
approved
frozen
deprecated
superseded
retired
```

任何进入实现或运行的 Artifact 必须具有批准状态和 lineage。

## 5.4 Requirement ID / Semantic Pointer

每一项工程要求都必须绑定 Requirement ID 和 Semantic Pointer。Field、Algorithm、Parameter、Schema、Code、Test 和 Runtime Evidence 必须可追溯到对应上游语义。

## 5.5 Version / Hash / Dependency / Supersedes

每个正式 Artifact 必须记录：

```text
version
hash 或等效完整性标识
dependency
supersedes
retained / deprecated / retired 状态
```

## 5.6 Runtime Binding / Evidence Link

任何运行对象都必须能够绑定到唯一的规范版本、代码版本、模型版本、参数版本和 runtime configuration，并能关联运行证据。

# 6. 系统架构、系统平面与工具职责

## 6.1 Lifecycle Plane × Functional Plane Matrix

系统架构必须以 Lifecycle Plane × Functional Plane Matrix 表达研究、工程与运行活动如何穿过 Data、Domain / State、Decision / Governance、Execution、Observability、Control / Release 与 Human Interaction 等功能平面。

系统架构平面可按部署与工具边界描述为 Research Plane、Backtest / Replay Plane、Runtime Domain Plane、Live Execution Plane、Observability / AI Diagnostic Plane；该分类用于系统拓扑，不替代第 4.7 节的 Functional Planes。

## 6.2 系统边界

系统不能退化为行情看板、总 Greeks 表、回测程序或单一订单工具。系统维护的是随市场、持仓、成交和时间持续演化的组合状态，至少包含：

```text
Market State
Ledger State
Structure State
Greeks / Risk State
Governance State
Execution State
Audit State
```

## 6.3 工具职责矩阵

| 工具 | 正式职责 | 禁止职责 |
|---|---|---|
| IBKR | 行情、账户、持仓、订单、成交外部事实源；最终执行通道 | 内部结构、诊断、参数或治理权威 |
| Python Domain Kernel | 账本、结构、风险、诊断、候选、治理、审计 | 保存唯一生产状态；直接依赖前端 |
| FastAPI | 前端、脚本和后端服务之间的统一接口 | 承担核心策略计算和状态权威 |
| PostgreSQL | 内部事务状态、账本、事件、审批、执行、审计权威源 | 高密度历史期权链和大规模回测数据 |
| Parquet / DuckDB | 历史数据、研究、回测、情景矩阵、盘后分析 | 订单生命周期、审批和生产事务 |

| GitHub / CI | 版本、测试、发布和工程治理 | 盘中热路径 |
| LLM / Codex / Claude | 研发协作、审计、盘后解释 | 实时行情、风险、审批、执行和 kill switch 热路径 |

## 6.4 Authoritative Source 与唯一 Writer

| 对象 | 权威源 |
|---|---|
| 外部行情、账户、持仓、订单、成交 | IBKR |
| 内部账本、结构、诊断、候选、审批、执行状态 | PostgreSQL |
| 大规模历史行情、期权链、情景矩阵 | Parquet / DuckDB |
| 研究结果与代码版本 | GitHub Release / Research Artifact |
| 参数和规则版本 | Parameter Registry / Rule Registry |

唯一 Broker Writer 必须是 Python Execution Service。Excel、Streamlit 和未来规则引擎都不能直接向 IBKR 发送订单。

## 6.5 读写权限和工具间接口

所有工具间接口必须声明：

```text
读取对象；
写入对象；
是否具备外部副作用；
是否可进入生产；
是否可修改状态；
是否需要人工批准；
是否留下审计证据。
```

## 6.6 工具不变量

工具不得通过可视化、临时脚本、Excel 公式、LLM 输出或研究 notebook 改写生产状态、生产参数、治理裁决或执行状态。

## 6.7 工具故障与降级

工具故障必须有降级策略。至少覆盖：

```text
IBKR 断线；
行情 stale；
数据库不可用；
Excel 前端不可用；
监控不可用；
执行服务未知状态；
人工接管。
```

## 6.8 工具替换、升级与退役

工具替换、升级和退役必须进入 Change / Migration / Retirement 流程，不得通过直接替换软件组件改变对象身份、账本语义、参数含义或执行权限。

# 7. 数据架构、时间语义与数据治理

## 7.1 数据对象分类

数据对象至少分为：

```text
Market Data
Contract Data
Account Data
Position Data
Order Data
Fill Data
Ledger Data
Derived Risk Data
Diagnostic Data
Candidate Data
Governance Data
Runtime Evidence
```

## 7.2 数据权威矩阵

每类数据必须声明 Source of Truth、复制源、缓存、修订源、对账源和退役规则。

## 7.3 Data Contract

核心模块之间不得传递裸 `price`、裸 `iv` 或裸 `risk`。数据对象必须包含身份、来源、时间、单位、质量标识和 lineage。

## 7.4 时间语义与市场日历

必须区分：

```text
event_time

snapshot_time
bar_start_time
bar_end_time
broker_time
system_time
```

并显式处理时区、DST、market session、market calendar、期权到期、last trading day 和 settlement time。

## 7.5 数据质量与 Freshness

数据质量规则必须覆盖：

```text
stale quote；
缺失值；
重复数据；
乱序数据；
回补数据；
异常 bid / ask；
last 替代；
跨资产快照不同步；
source conflict；
freshness breach。
```

## 7.6 Data-to-Domain Bridge

Data-to-Domain Bridge 负责将外部数据转换为内部 Domain Event / Domain State。该转换不得引入策略语义，不得将数据清洗结果直接写成 diagnostic 或 candidate。

## 7.7 Research / Exploratory Backtest / Production-path Validation / Replay / Live 数据关系

不同模式的数据使用必须显式声明：

```text
数据源；
快照规则；
延迟假设；
可用字段；
修订规则；
是否允许未来信息；
是否写入生产状态；
是否具有外部副作用。
```

## 7.8 数据修订、Lineage 与可重放

任何数据修订必须记录修订来源、修订时间、影响范围和下游重算要求。Replay 必须能够绑定初始状态、事件序列、代码版本、Schema 版本、模型版本和参数集。

## 7.9 存储、生命周期、备份、恢复与归档

数据生命周期必须覆盖热数据、冷数据、研究数据、审计证据、迁移归档和退役归档。备份和恢复必须有验证证据。

# 8. 领域对象、Field 与 Engineering Contract

## 8.1 Domain Object

Domain Object 是系统维护的内部对象，不等于 Broker 原生对象、数据库表或前端展示行。每个 Domain Object 必须有身份、状态、生命周期、权限和不变量。

## 8.2 Field Taxonomy

Field 必须由已批准的上游语义和 Taxonomy 单向下沉形成。字段不得擅自增加策略含义，不得把观察项写成治理裁决，不得把 report module title 写成 production field。

## 8.3 类型、单位与身份

字段命名和类型必须显式包含单位与口径。禁止在核心模型中使用未锁定语义的通用字段名，例如：

```text
value
size
risk
premium
iv
exposure
```

## 8.4 Invariant

每个 Domain Object、Field、Interface 和 State Contract 必须声明不变量。违反不变量时必须阻断、降级或进入人工复核，不得静默修正。

## 8.5 Event / State Contract

Event 与 State 必须区分。系统必须区分：

```text
交易意图；
订单请求；
Broker Order；
成交记录；
持仓结果。
```

这五类对象不能压缩成一个通用 `order` 对象。

## 8.6 Field / Interface / Machine Schema

Field / Interface / Machine Schema 必须由专业子规范生成，并通过 Schema / API / State Machine / Database Constraint 落实为机器可读合同。

## 8.7 环境可用性

每个字段和接口必须声明在 Research、Production-path Historical Validation、Replay、Paper、Shadow、Limited Live、Production Live 中是否可用、是否可写、是否可作为治理输入。

## 8.8 Field / Interface / Schema Contract Gate

字段、接口和机器合同进入实现前，必须通过 Contract Gate，验证：

```text
上游语义指针；
Taxonomy 准入；
类型和单位；
状态生命周期；
环境可用性；
禁止自动化；
测试和 runtime evidence 要求。
```

# 9. 模型、参数与 Research-to-Live 治理

## 9.1 Model / Parameter Taxonomy

必须区分模型、参数、参数槽、候选参数集、生产参数集、运行时参数和配置。参数不得隐藏在算法或代码中。

## 9.2 Model / Parameter Registry

所有可调数值、阈值、窗口、容忍带和等价规则必须进入 Model / Parameter Registry，记录来源、适用范围、版本、回测证据、批准状态和回滚路径。

## 9.3 Calibration / Applicability Domain

模型与参数必须声明校准方法、适用域和失效条件。适用域不能由研究回测收益单独证明。

## 9.4 Tolerance Band

Tolerance Band 必须作为可治理对象注册，不得以硬编码常量隐藏在算法或部署配置中。

## 9.5 Promotion

候选参数集进入生产前必须经过参数治理、审批、版本记录和上线流程。candidate parameter set 不等于 production parameter set。

## 9.6 Production Runtime Binding / Validation Runtime Binding

必须区分：

```text
Production Runtime Binding：绑定生产 core version、parameter set、profile、account、broker 和 runtime mode。
Validation Runtime Binding：绑定验证使用的代码、Schema、模型、参数和无外部副作用配置。
```

二者必须保持版本一致性，同时隔离生产外部副作用。

## 9.7 Drift / Recalibration

模型漂移、参数漂移和适用域漂移必须进入质量维护闭环或 Change Gate，不得由盘中临时修正覆盖。

## 9.8 Fallback / Rollback / Retirement

每个生产模型和参数集必须具有 fallback、rollback 和 retirement 规则；旧持仓、旧状态和旧证据必须可解释。

# 10. Workflow、事件、状态机与执行治理

## 10.1 Workflow Catalog

系统主链为：

```text
External Fact
→ Internal State Reconstruction
→ Ledger / Structure / Risk State
→ Target–Actual Gap
→ Diagnostic
→ Candidate Package
→ Constraint Stack
→ Approval / Block / Manual Review / No Action
→ Execution
→ Fill
→ State Rebuild
→ Post-action Audit
```

## 10.2 Event / State Taxonomy

事件和状态必须具有独立 taxonomy。事件描述发生了什么，状态描述系统在某一时点的受控表达。

## 10.3 State Machine / Action Lifecycle

订单状态机至少包含：

```text
CREATED
→ VALIDATED
→ SUBMITTING
→ ACKNOWLEDGED
→ PARTIALLY_FILLED
→ FILLED
→ CANCEL_PENDING
→ CANCELLED
→ REJECTED
→ UNKNOWN
```

`UNKNOWN` 必须是正式状态。遇到未知状态时，必须先与 Broker 对账，禁止直接重试。

## 10.4 Precondition / Postcondition

任何 action 必须声明 precondition 与 postcondition。执行前必须校验前置条件，执行后必须进行 post-action legality check。

## 10.5 Idempotency / Retry / Concurrency

每个交易意图必须拥有唯一 `intent_id`。Retry 必须基于幂等设计和 Broker 对账，不得因 API timeout 直接重复下单。

## 10.6 Partial Fill / Cancel / Replace

partial fill、cancel pending、replace、reject 和 unknown 必须有正式状态迁移和补偿流程。组合订单部分成交不得静默补腿。

## 10.7 Recovery / Compensation

恢复和补偿必须以真实 fill 与 Broker 状态为依据，不能以计划成交或本地假设更新持仓。

## 10.8 Human-in-the-loop Operational Contract

B 级半自动执行中，人工批准是正式运行合同的一部分。人工批准、人工接管和异常 override 都必须留下证据。

## 10.9 Decision-to-Execution

Decision-to-Execution Bridge 必须阻断以下短路：

```text
行情字段 → 订单；
单一 Greek → 订单；
diagnostic → 订单；
candidate → 订单；
审计结果 → 下一笔订单。
```

---

# 11. 质量、验证、反例与 Observability

## 11.1 Requirement / Invariant / Counterexample

正向 Specification 必须与反例 / Failure Contract 同步维护。Bug 应被治理为正式 Failure / Counterexample Module，而不是零散事后修复记录。

## 11.2 Failure Contract / Test Oracle

每个核心合同必须有 Failure Contract 与 Test Oracle。测试必须能判断何时失败，而不是只验证正常路径可运行。

## 11.3 Unit / Integration / Contract / Property / Negative Test

测试体系至少包括：

```text
Unit Test
Integration Test
Contract Test
Property Test
Negative Test
Regression Test
```

## 11.4 Deterministic Replay / Failure Injection

Deterministic Replay 必须用于复现状态迁移、Incident、迁移结果和环境晋升证据。Failure Injection 必须覆盖数据、订单、状态、参数、连接和恢复路径。

## 11.5 Exploratory Research Backtest / Production-path Historical Validation

Exploratory Research Backtest 证明研究假设和参数可行性；Production-path Historical Validation 验证生产路径实现。两者必须明确区分。

## 11.6 Runtime Guard

Runtime Guard 必须覆盖数据新鲜度、对象身份、权限边界、状态迁移、参数版本、执行前条件、执行后状态和 forbidden automation。

## 11.7 Log / Metric / Trace / Alert

Observability 至少包含：

```text
Log
Metric
Trace
Alert
Audit Event
Runtime Evidence
```

监控指标不得替代治理裁决。

## 11.8 Incident Evidence

Incident 必须记录时间线、影响范围、触发条件、状态快照、受影响版本、恢复过程、根因、修复、回归测试和约束上提结果。

## 11.9 Operational Resilience

Operational Resilience 覆盖系统可用性、降级、恢复、备份、对账、人工接管、RTO / RPO 和恢复演练。

---

# 12. Release、Change、Migration、Rollback 与 Retirement

## 12.1 Change Proposal / Specification Diff

任何正式变更必须形成 Change Proposal 和 Specification Diff。变更不得只以代码 diff 表达。

## 12.2 Compatibility Analysis

变更必须分析与旧字段、旧状态、旧参数、旧代码、旧证据和旧持仓的兼容性。

## 12.3 Release Candidate / Build / Deployment Artifact

Release Candidate 必须绑定规范版本、代码版本、Schema 版本、参数版本、测试证据和部署 Artifact。

## 12.4 Migration Plan / Parallel Run / Cutover

Migration Plan 必须说明迁移对象、迁移规则、验证方法、parallel run、cutover 条件和失败回退路径。

## 12.5 Rollback / Fallback

Rollback / Fallback 必须可执行、可验证、可审计。回滚后旧状态和旧证据必须保持可解释。

## 12.6 Deprecation / Retirement

Deprecation 与 Retirement 必须进入正式流程。退役对象不得继续作为生产权威源或隐性依赖。

## 12.7 Historical Interpretability

新版本必须能够解释旧持仓、旧状态、旧 runtime evidence 和历史审计材料。

# 13. 权限、安全、角色与禁止自动化

## 13.1 Role Model / RACI

系统必须定义角色模型和 RACI，至少覆盖：

```text
Owner
Approver
Executor
Reviewer
Auditor
Operator
AI Agent
Emergency Override Authority
```

## 13.2 Read / Write Scope

每个角色和工具必须声明读取范围、写入范围、执行权限和禁止权限。

## 13.3 Approval / Override Authority

approval、block、manual review、rollback、release、override 和 retirement 必须有明确批准权。

## 13.4 Human Approval / Exceptional Override Contract

人工批准和异常 override 必须记录理由、范围、有效期、受影响对象、证据和回退条件。异常 override 不得变成永久规则。

## 13.5 Release / Rollback Authority

发布和回滚权限必须独立于生成方。生成方不得单独批准自身产物进入生产。

## 13.6 AI Agent Permission

AI Agent 不得进入实时行情、风险、审批、执行和 kill switch 热路径。AI 可用于研发协作、审计、盘后解释、测试生成和修复建议，但不得直接下单或覆盖治理裁决。

## 13.7 Forbidden Automation

Forbidden Automation 至少包括：

```text
diagnostic 自动下单；
candidate 自动下单；
post-action audit 触发下一笔交易；
单一 proxy / Greek 生成 approved action；
研究结果自动上线；
LLM 直接修改生产参数；
profile / YAML / runtime 覆盖 strategy core。
```

## 13.8 Independent Audit

关键变更、阶段晋升、发布、迁移、回滚和退役必须有独立审计。审计证据不得由生成方单独提供。

# 14. Normative Level、Conformance Profile、Deployment Profile 与自动化等级

## 14.1 Normative Level

Normative Level 表示要求强度：

```text
MUST
SHOULD
MAY
```

## 14.2 Applicable Profile

Applicable Profile 表示要求适用范围：

```text
Core
B-Level
C-Level
Optional-Advanced
```

Core 为不可删除的核心控制。B-Level 对应半自动执行，C-Level 对应规则自动执行，Optional-Advanced 为高级能力，不得削弱 Core。

## 14.3 Applicability Disposition

Applicability Disposition 包括：

```text
Applicable
Reserved
Not Applicable
```

Not Applicable 必须说明理由，不得用于规避 Core 控制。

## 14.4 Profile 组合、继承与等效替代

Profile 可以组合、继承或通过等效控制替代，但必须保持核心控制不被削弱。

## 14.5 Control Equivalence Assessment

Control Equivalence Assessment 必须证明替代方案在控制目标、证据、Gate 和失效处理上等效。

## 14.6 Requirement 三元正交标注

每项要求必须同时标注：

```text
Normative Level
Applicable Profile
Applicability Disposition
```

## 14.7 Deployment Profile

Deployment Profile 绑定部署差异、账户差异、broker 差异、自动化等级和非功能性数值约束。

## 14.8 Automation Grade 与 Runtime Binding

B 级与 C 级应共用同一后端，差异位于 Approval Policy：

```text
B级：ManualApprovalPolicy
C级：RuleBasedApprovalPolicy + ManualReviewFallback
```

Automation Grade 必须进入 Runtime Binding。

# 15. 代码前工程循环

## 15.1 Semantic / Taxonomy Readiness

代码前必须确认上游语义和 Taxonomy 已达到相应准备度。未通过准入 Gate 的对象不得进入字段冻结、算法设计或实现。

## 15.2 Architecture / Data / Domain / Event / State Contract

代码前必须形成架构、数据、领域对象、事件和状态合同，使 AI Coding Agent 无须自行猜测业务含义，也不能通过技术选择改变策略语义。

## 15.3 Field / Interface / Machine Schema Contract

Field、Interface 和 Machine Schema 必须在编码前完成合同定义，并声明类型、单位、身份、不变量、环境可用性和证据要求。

## 15.4 Algorithm / Model / Parameter / Workflow Contract

算法、模型、参数和 Workflow 必须分离。可调数值不得隐藏在算法或代码中。

## 15.5 Failure / Verification / Observability Design

失败合同、反例、测试、Runtime Guard、Log、Metric、Trace、Alert 必须在编码前设计。

## 15.6 Coding Readiness Gate

Coding Readiness Gate 必须验证：

```text
语义指针完整；
Taxonomy 准入完整；
字段和接口合同完整；
模型和参数合同完整；
Workflow 和状态机完整；
反例和测试设计完整；
禁止自动化已落实；
AI Coding 任务边界清楚。
```

# 16. 代码中工程循环

## 16.1 Contract-first / Schema-first

实现必须采用 Contract-first / Schema-first。代码不得自行定义业务语义。

## 16.2 AI Coding Task Pack

AI Coding Task Pack 必须包含：

```text
目标；
输入文件；
输出文件；
禁止项；
依赖版本；
接口合同；
测试要求；
验收标准；
不得修改范围。
```

## 16.3 代码架构与依赖方向

代码依赖方向必须服从语义—工程—实现下沉链。Domain Kernel 不得依赖前端、Broker 原生对象或研究环境原生对象。

## 16.4 类型、单位、事务、幂等

实现必须显式处理类型、单位、事务、幂等、并发、retry、unknown state 和恢复路径。

## 16.5 Test / Log / Metric 同步交付

代码、测试、日志、指标和 runtime guard 必须同步交付。没有测试和证据的实现不得进入发布候选。

## 16.6 CI / Independent Audit

CI 必须执行格式、类型、Schema、单元测试、合同测试、负向测试和回归测试。关键实现必须有独立审计。

## 16.7 Build / Deployment Artifact

构建产物必须绑定代码版本、Schema 版本、参数版本、依赖版本、测试结果和部署配置。

## 16.8 构建期 Defect 闭环

构建期 Defect 必须进入 Defect-to-Constraint Bridge：

```text
Defect
→ Reproduction
→ Counterexample
→ Invariant / Contract Update
→ Test
→ Fix
→ Regression Evidence
```

# 17. 代码后工程循环

## 17.1 Deterministic Replay

Deterministic Replay 必须用于证明状态迁移可重放、Incident 可复现、迁移可验证。

## 17.2 Production-path Historical Validation

Production-path Historical Validation 必须使用受控实现、受控参数、受控事件合同和生产路径逻辑。

## 17.3 Paper / Shadow / Limited Live / Production Live

环境晋升顺序为：

```text
Paper
→ Shadow
→ Limited Live
→ Production Live
```

每一模式必须有 Runtime Mode Contract、证据输出、晋升条件和回退条件。

## 17.4 环境晋升

环境晋升不得只依据收益表现。必须通过状态一致性、执行链、对账、运行证据、异常处理和人工接管验证。

## 17.5 实盘状态闭环

实盘运行必须持续执行：

```text
运行事件
→ 状态重建
→ 诊断
→ 候选
→ 治理
→ 执行
→ fill
→ 状态重建
→ post-action audit
```

## 17.6 Fill-based State Reconstruction

执行后状态必须基于真实 fill 重建，不得以计划订单或本地假设更新。

## 17.7 Broker Reconciliation

系统必须与 Broker 进行持仓、订单、成交、现金和保证金对账。对账差异必须进入 Incident 或 Manual Review。

## 17.8 Data / Model Drift

Data Drift 与 Model Drift 必须有检测、记录、处理和回到上游 Gate 的机制。

## 17.9 Incident / Problem / Change

Incident 必须区分即时恢复、根因分析、问题管理和正式 Change。不能用临时修复替代约束上提。

## 17.10 Release / Rollback / Migration / Retirement

运行后变更必须通过 Release、Rollback、Migration、Retirement 流程保持版本连续性。

## 17.11 Runtime Evidence

Runtime Evidence 必须覆盖：

```text
Event
State
Decision
Order
Fill
Audit
Incident
Replay
Reconciliation
Migration
Retirement
```

# 18. 八个关键连接层

## 18.1 Semantic-to-Taxonomy Bridge

将语义权威中的对象、权限和禁止项转译为 Taxonomy 边界。

## 18.2 Taxonomy-to-Engineering Bridge

将已批准 Taxonomy 安全下沉到 Field、Algorithm、Parameter、Data、Model、Workflow 和 Governance 子规范。

## 18.3 Data-to-Domain Bridge

将外部数据转译为内部 Domain Event / Domain State，并防止数据清洗越权为诊断或动作。

## 18.4 Research-to-Live Translation Bridge

将研究证据、参数候选和模型假设转译为可验证、可回滚、可绑定的生产对象。

## 18.5 Semantic-to-Runtime Traceability Bridge

保证每个 runtime object、decision、order、fill、incident 和 audit evidence 能回溯到上游语义与工程合同。

## 18.6 Decision-to-Execution Bridge

保证 candidate、governance decision、approved action、order request、broker order 和 fill 分层，不发生直接短路。

## 18.7 Defect-to-Constraint Bridge

将 Bug、Near Miss、Incident 和反例上提为不变量、合同、测试和 Runtime Guard。

## 18.8 Version-to-Version Migration Bridge

保证新旧版本之间的状态、持仓、参数、证据和解释连续。

# 20. Stage-Gate 与环境晋升

## 20.1 G0–G8 建设 Gate（含 G5A / G5B / G5C）

建设 Gate 覆盖从语义准备、Taxonomy 准入、工程合同、机器合同、编码准备、实现、测试到构建产物的全过程。

## 20.2 G9A / G9B 验证 Gate

```text
G9A：Deterministic Replay Gate
G9B：Production-path Historical Validation Gate
```

Exploratory Research Backtest 属于研究证据闭环，用于形成研究假设、参数候选、稳定区间和反例路径，不作为实现完成后的环境晋升 Gate。

## 20.3 G10A / G10B / G11 / G12 环境晋升 Gate

```text
G10A：Paper Gate
G10B：Shadow Gate
G11：Limited Live Gate
G12：Production Live Gate
```

每个 Gate 必须有输入、输出、阻断条件和回退路径。

## 20.4 CG / MG / RG 横向治理 Gate

```text
CG：Change Gate
MG：Migration Gate
RG：Retirement Gate
```

横向 Gate 可将变更路由回任意受影响建设或验证 Gate。

## 20.5 Change Classification and Return-Path Matrix

系统必须维护 Change Classification and Return-Path Matrix，将字段、算法、参数、模型、数据、状态机、部署、权限和文档变更路由回相应 Gate。

## 20.6 G3 / G4 合同边界

G3 与 G4 必须明确区分 Engineering Contract 与 Machine-readable Contract。不得以机器 Schema 替代工程语义合同。

## 20.7 Gate 元合同

每个 Gate 必须声明：

```text
输入 Artifact；
输出 Artifact；
验证项；
阻断条件；
批准角色；
Runtime Evidence；
失败返回路径；
waiver 条件。
```

## 20.8 Blocking Conditions

阻断条件至少包括：

```text
缺少 canonical source；
权限标注缺失；
存在 forbidden automation；
字段或算法越权；
参数未注册；
测试缺失；
runtime evidence 不足；
状态不可重放；
旧版本不可解释。
```

## 20.9 Gate Fail、返回上游与重新准入

Gate 失败必须明确返回上游路径和重新准入条件，不得以局部修补直接越过 Gate。

## 20.10 Waiver Policy

Waiver 只能用于有限、记录、批准、可回收的例外，不得覆盖 Core 控制或策略身份约束。

## 20.11 Rollback / Fallback / Promotion Evidence

任何晋升必须同时提供 rollback、fallback 和 promotion evidence。缺失回退证据不得进入更高运行模式。

# 21. 子规范分解与一般下沉规则

## 21.1 总纲与子规范颗粒度边界

总纲只定义专业域、生命周期、连接层、闭环、Gate、Artifact 和证据要求。子规范定义具体字段、接口、算法、模型、参数、数据、事件、状态机、测试和部署配置。

## 21.2 Field / Algorithm 下沉规则

Field 与 Algorithm 必须经 Taxonomy Bridge 准入，并绑定 Semantic Pointer、权限标注、不变量、测试和 runtime evidence。

## 21.3 Parameter / Model 分离规则

Parameter 与 Model 必须与 Algorithm 分离。参数进入 Registry，模型进入 Model Contract，算法只读取已绑定版本。

## 21.4 Data / Event / State 下沉规则

Data、Event、State 必须分别定义，不得把外部数据、内部状态、诊断输出和执行动作压缩为同一对象。

## 21.5 标准子规范模板

标准子规范至少包含：

```text
文档定位；
适用范围；
canonical source；
对象定义；
权限边界；
合同定义；
不变量；
禁止项；
测试要求；
Gate；
Artifact；
Runtime Evidence；
版本和变更规则。
```

## 21.6 交叉一致性审计

交叉一致性审计必须检查：

```text
语义是否反向改写；
Taxonomy 是否被越权；
字段、算法、参数是否重复定义；
运行模式是否混淆；
Profile 是否削弱 Core；
Gate 是否缺失；
Runtime Evidence 是否可追溯。
```

## 21.7 版本、哈希与依赖管理

所有正式子规范和机器可读合同必须记录版本、哈希或等效完整性标识、依赖、supersedes、retained / deprecated / retired 状态。

# 附录 B. 最终定位

这份总纲的最终作用可以压缩为：

> **以元治理层覆盖语义—Taxonomy—工程—运行全链，将已经批准的策略语义内核装配成一套以专业控制域为主体、以代码前/中/后为工程生命周期、以 Lifecycle Plane × Functional Plane 为系统平面矩阵、以运行与验证模式为实例化方式，并从语义、工具、数据、领域、模型、参数、Workflow、质量、权限、版本、代码到实盘运行、维护和升级均可追溯、可验证、不可越权漂移的完整工程体系。**
